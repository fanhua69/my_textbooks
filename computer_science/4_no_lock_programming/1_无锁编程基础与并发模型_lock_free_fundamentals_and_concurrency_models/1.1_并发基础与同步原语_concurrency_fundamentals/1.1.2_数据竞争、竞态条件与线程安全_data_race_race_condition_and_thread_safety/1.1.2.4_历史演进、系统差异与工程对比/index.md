# 1.1.2.4 历史演进、系统差异与工程对比

> **简介**：| 对比维度 | Data Race（数据竞争） | Race Condition（竞态条件） | | --- | --- | --- | | 定义层级 | 语言内存模型层（无同步并发读写同一内存且含写） | 程序逻辑与时序层（结果依赖线程执行/到达顺序） | | C++ 标准后果 | 未定义行为（UB），程序行...

---

### 历史演进脉络

* **早期单线程与锁时代**：在多核普及之前，并发问题主要集中在中断、信号与多任务切换；引入 `pthread_mutex` 等原语后，主流做法是通过互斥锁串行化对共享数据的访问。
* **C++11 统一内存模型**：C++11 首次在语言层面定义了内存模型、原子类型（`std::atomic`）与 Data Race / `happens-before` 语义，结束了此前高度依赖平台方言与隐式假设的状态。
* **现代高并发与无锁演进**：随着多核规模扩大与低延迟需求提升，工程实践在锁之外进一步引入无锁队列、原子状态机与安全内存回收，但对 Data Race 零容忍、对 Race Condition 严格建模始终是底线。

### 系统与工具链差异

* **编译器与 Sanitizer 支持**：GCC、Clang 与 MSVC 对 C++11/17/20/23 原子与内存模型的支持已较为成熟，但不同架构（x86_64 vs. ARM64）下未同步代码的表现可能迥异。Linux 与 macOS/BSD 上均可使用 Clang/GCC 的 TSan 进行竞态检测，但需注意系统库与动态链接场景下的插桩限制。
* **排查手段对比**：逻辑层面的 Race Condition 往往难以靠单次单元测试稳定复现，通常需要结合压力测试、线程交错注入、日志时序分析与 TSan 共同定位。

### Data Race 与 Race Condition 工程对比

| 对比维度 | Data Race（数据竞争） | Race Condition（竞态条件） |
| --- | --- | --- |
| **定义层级** | 语言内存模型层（无同步并发读写同一内存且含写） | 程序逻辑与时序层（结果依赖线程执行/到达顺序） |
| **C++ 标准后果** | **未定义行为（UB）**，程序行为完全失去标准保证 | 通常是**逻辑 Bug**（如丢更新、状态错乱、重复处理），未必触发 UB |
| **修复手段** | 使用 `std::atomic`、互斥锁、线程隔离或不可变数据建立同步 | 扩大原子/临界区范围、使用 CAS 重试、引入状态机/版本号/序列号 |
| **检测方式** | TSan（`-fsanitize=thread`）、代码审查与内存模型分析 | 并发压测、边界时序测试、状态不变量断言与日志追踪 |
