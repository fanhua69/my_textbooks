# 1.1.4.1 条件变量（Condition Variable）：谓词等待与唤醒机制

**介绍**: > **简介**：条件变量本身不是锁，而是与互斥锁配合使用的阻塞等待与事件通知机制：它允许线程在某个共享状态谓词（Predicate）尚未满足时休眠让出 CPU，并在其他线程修改状态后被唤醒重新检查条件。

## 为什么条件变量必须搭配 `std::unique_lock<std::mutex>`？

条件变量（`std::condition_variable`）本身不具备“状态记忆”和“互斥保护”能力，它只负责**挂起等待**与**唤醒通知**。要让“检查共享状态 -> 决定是否休眠”和“修改共享状态 -> 发出唤醒通知”这两个动作在多线程下不发生时序错乱，必须借助 `std::mutex` 保护共享状态，并用 `std::unique_lock<std::mutex>` 控制锁的**按需、原子性解锁与重新加锁**（`std::lock_guard` 不支持中途手动或自动释放/重获锁，因此不能传给 `cv.wait`）。

### 1. 防止“检查条件 -> 决定休眠”之间的竞态窗口（唤醒丢失 Lost Wakeup）

如果消费者线程先加锁检查队列为空，随后**释放锁**，紧接着还没来得及调用 `cv.wait()` 挂起自己，生产者线程就在这个空档期抢占执行、推入数据并调用了 `cv.notify_one()`：

* 生产者发出 `notify_one()` 时，消费者线程**尚未进入条件变量的等待队列**，这条唤醒信号就会被“丢弃”（条件变量不像信号量那样保存计数值）。
* 随后消费者线程才调用 `wait()` 让自己进入休眠，此时生产者已经发完通知甚至已经结束工作，消费者就会在没有新通知的情况下**永远阻塞卡死**。

搭配 `std::unique_lock<std::mutex>` 后，消费者在持锁状态下判断谓词不满足，再由 `cv.wait(lk, ...)` 在进入休眠队列的同时释放 `lk`，把“判断条件”和“加入等待队列 + 释放互斥锁”衔接起来，消除这个竞态窗口。

### 2. `wait()` 的原子性释放与重获

当谓词条件尚未满足时，线程不能拿着 `std::mutex` 去睡觉，否则其他线程连加锁修改共享状态的机会都没有，系统会直接死锁。反过来，如果“释放互斥锁”和“把线程放入条件变量等待队列并休眠”不是原子的，中间依然会插进其他线程的修改与唤醒。

`std::unique_lock<std::mutex>` 允许 `cv.wait()` 在内部完成以下关键步骤：

1. **检查谓词**（在已持有 `lk` 对应互斥锁的前提下，安全读取共享状态）。
2. 若谓词为 `false`：**原子地释放 `lk` 所持有的互斥锁，并将当前线程挂起**（让出 CPU，等待被 `notify_one` / `notify_all` 唤醒）。
3. 当线程被唤醒后：**在 `wait()` 返回前，重新获取 `lk` 所持有的互斥锁**，随后再次检查谓词（若带谓词重载）；最终 `wait()` 返回时，调用方线程是**重新持有锁**的状态，可以安全地继续读写受保护的共享数据。

### 3. 虚假唤醒（Spurious Wakeup）与循环检查

在 POSIX `pthread_cond_wait`、Windows 原生原语以及 C++ 标准库实现中，条件变量允许出现**虚假唤醒**——即线程在没有任何线程调用 `notify_one()` 或 `notify_all()` 的情况下被唤醒返回。此外，在多消费者场景下，即使某个线程被合法唤醒，也可能在重新抢回互斥锁之前，条件就已经被另一个先醒来的消费者抢先消费掉了。

因此：

* **绝不能用单次 `if` 代替循环/谓词**（若用 `if (!ready) cv.wait(lk);`，一旦发生虚假唤醒或条件被抢走，线程就会带着“条件其实不成立”的错误假设往下执行，引发逻辑错误甚至数据竞争/UB）。
* **必须使用带谓词的 `cv.wait(lk, pred)**`（其标准库语义等价于 `while (!pred()) { wait(lk); }`）或显式的 `while` 循环，每次醒来并重新拿锁后都重新验证条件是否真的成立。

## 示例代码：错误写法（唤醒丢失 / `if` 虚假唤醒）与正确写法（`std::unique_lock` + 谓词）

下面通过一个简化的单生产-单消费队列演示关键差异：

```cpp
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

// 1. 反面示例：存在唤醒丢失风险（检查与休眠之间释放了锁）及用 if 代替循环的风险
void buggy_consumer_demo() {
    std::mutex mtx;
    std::condition_variable cv;
    std::queue<int> q;
    bool done = false;

    std::thread producer([&]() {
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
        {
            std::lock_guard<std::mutex> lk(mtx);
            q.push(42);
            done = true;
        }
        cv.notify_one();
    });

    std::thread consumer([&]() {
        std::unique_lock<std::mutex> lk(mtx);
        // 错误示范：先解锁再 wait，若 producer 在这两行之间完成 push + notify_one，
        // 这里的 notify_one 就会丢失，consumer 可能卡死
        bool empty = q.empty() && !done;
        lk.unlock();

        if (empty) {
            std::this_thread::sleep_for(std::chrono::milliseconds(20)); // 人为放大竞态窗口
            lk.lock();
            // 即便走到这里，若用 if 而不是 while/谓词，遇到虚假唤醒或状态变化也会出错
            if (q.empty() && !done) {
                cv.wait(lk);
            }
            lk.unlock();
        }

        lk.lock();
        if (!q.empty()) {
            std::cout << "[Buggy] popped: " << q.front() << "\n";
            q.pop();
        } else {
            std::cout << "[Buggy] queue empty (possible lost wakeup)\n";
        }
    });

    producer.join();
    consumer.join();
}

// 2. 推荐写法：std::unique_lock<std::mutex> + 谓词（等价于 while 循环检查）
void safe_producer_consumer_demo() {
    std::mutex mtx;
    std::condition_variable cv;
    std::queue<int> q;
    bool finished = false;

    std::thread producer([&]() {
        for (int i = 1; i <= 5; ++i) {
            {
                std::lock_guard<std::mutex> lk(mtx);
                q.push(i * 10);
            }
            cv.notify_one();
        }
        {
            std::lock_guard<std::mutex> lk(mtx);
            finished = true;
        }
        cv.notify_all();
    });

    std::thread consumer([&]() {
        while (true) {
            std::unique_lock<std::mutex> lk(mtx);

            // 谓词保证：
            // 1) 不会因虚假唤醒提前退出；
            // 2) wait 内部原子释放 lk 并挂起，唤醒后重新持有 lk 再检查谓词；
            // 3) 返回时 lk 处于锁定状态，可安全访问 q 和 finished。
            cv.wait(lk, [&]() { return !q.empty() || finished; });

            while (!q.empty()) {
                int val = q.front();
                q.pop();
                std::cout << "[Safe] popped: " << val << "\n";
            }

            if (finished && q.empty()) {
                break;
            }
        }
    });

    producer.join();
    consumer.join();
}

int main() {
    buggy_consumer_demo();
    safe_producer_consumer_demo();
    return 0;
}

```

## 补充工程细节

* **先改状态、再发通知**：通常在修改共享状态并释放互斥锁**之后**调用 `notify_one()` / `notify_all()`（如上面 `safe_producer_consumer_demo` 中用花括号限定 `std::lock_guard` 作用域，出作用域自动解锁后再 `notify_one()`），这样被唤醒的线程重新拿锁时无需再等通知方解一次锁，能减少不必要的锁争用。
* **需要自定义锁类型时用 `std::condition_variable_any**`：`std::condition_variable` 仅接受 `std::unique_lock<std::mutex>`；若要搭配其他可解锁概念的锁包装器，可使用 `std::condition_variable_any`，但通常开销略高，常规场景优先使用 `std::condition_variable` + `std::unique_lock<std::mutex>`。

**条件变量**本身不是锁，而是**与互斥锁配合使用的阻塞等待与事件通知机制**：它允许线程在某个共享状态谓词（Predicate）尚未满足时休眠让出 CPU，并在其他线程修改状态后被唤醒重新检查条件。

## 为什么条件变量必须搭配 `std::unique_lock<std::mutex>`？

* **防止“检查条件 -> 决定休眠”之间的竞态窗口**：若线程先检查队列为空、释放锁，再准备调用 `wait()` 休眠，期间另一个线程可能刚推入数据并调用了 `notify_one()`——这会导致**唤醒丢失（Lost Wakeup）**，等待线程永远卡死。
* **`wait()` 的原子性释放与重获**：`cv.wait(lk, pred)` 会在谓词为 `false` 时，原子地释放互斥锁并把当前线程挂起；当被唤醒后，返回前会重新获取互斥锁，再检查谓词。
* **虚假唤醒（Spurious Wakeup）与循环检查**：操作系统或标准库实现允许条件变量在没有显式 `notify` 的情况下唤醒等待线程，或者多个线程被唤醒后抢先被其他线程消费掉条件。因此**必须使用谓词或 `while` 循环**，绝不能用单次 `if` 代替谓词判断。

## `notify_one()` 与 `notify_all()` 的选择

* **`notify_one()`**：唤醒至少一个正在等待的线程（若当前无等待线程，通知会被丢弃，不会像信号量那样累积许可）。适合只有一个消费者能处理该事件或只需推进一个工作者的场景。
* **`notify_all()`**：唤醒所有正在等待的线程，适合广播状态变更（例如全局退出标志置位、配置快照切换、多条件谓词变化）。在高并发下盲目 `notify_all()` 容易引发**惊群效应（Thundering Herd）**，大量线程醒来后争抢同一把互斥锁却只有少数能推进。
