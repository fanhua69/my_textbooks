从早期单核分时系统与多进程并发模型，演进到现代多核 SMP/NUMA 架构下的多线程与无锁编程，核心矛盾始终围绕**吞吐率、尾延迟（Tail Latency）与并发正确性**展开。

### 历史演进脉络

- **单核分时与进程并发**：早期系统受限于单核硬件，并发主要依赖时间片轮转调度；多进程模型强调故障隔离与独立地址空间，适合相互独立的任务或服务进程。
- **多核对称多处理（SMP）与多线程**：多核普及后，多线程成为榨取多核算力的主流方式，但也把缓存一致性、锁争用与线程调度抖动推到前台。
- **无锁与低延迟并发工程**：在对延迟敏感的系统中，开发者逐步引入原子操作、无锁队列与安全内存回收技术（如 Epoch-Based Reclamation、Hazard Pointer、RCU），以减少锁竞争带来的阻塞与调度不确定性。

### 操作系统与架构差异

- **调度器、同步原语与内存序**：Linux 与 macOS/BSD 在线程调度策略、内核同步原语及系统调用接口上存在差异；x86_64 与 ARM64 在内存序模型与缓存行/预取行为上也各有特点。编写跨平台底层组件时，应将系统调用与平台相关细节封装在统一接口后。
- **性能剖析与诊断工具差异**：排查并发瓶颈与延迟毛刺时，Linux 生态常用 `perf`、`ftrace`、`cyclictest`、ThreadSanitizer（TSan）等工具；macOS/BSD 生态则有 `kqueue`、系统剖析工具以及 Sanitizer 工具链。熟悉目标平台的观测手段，能避免盲目猜测瓶颈所在。

### 互斥锁与无锁设计的工程对比

| 维度 | 互斥锁 / 传统同步（Mutex / Condvar） | 无锁设计（Lock-Free / Atomic） |
| :--- | :--- | :--- |
| **心智模型与维护成本** | 相对直观，适合保护复杂多变量不变量 | 推理难度高，需严格分析内存序、ABA 与交错执行 |
| **阻塞与调度影响** | 锁被持有或发生争用时，等待线程可能阻塞/休眠，受调度延迟与优先级反转影响 | 至少有一个线程能在有限步内推进；热路径通常无锁阻塞，但需注意自旋开销与公平性 |
| **内存管理复杂度** | 持有锁期间通常更容易确定对象生命周期 | 并发读/遍历期间节点可能被其他线程摘除，需配合 Hazard Pointer、EBR、RCU 或安全回收策略 |
| **适用场景** | 低/中度争用、复杂状态组合、逻辑优先于极致微秒级延迟的业务 | 高并发热路径、低延迟队列/计数器/状态发布、经充分压测与检查验证的核心组件 |

> **工程建议**：不要为了“无锁”而无锁。优先保证逻辑清晰、无数据竞争与可测试性；只有在性能剖析确认为锁争用或同步延迟瓶颈，且能够掌控内存序与内存回收复杂度时，再将关键热路径演进为无锁结构。
