# 1.1.5.1 锁竞争的成因、微观开销与吞吐退化

**介绍**: > **简介**：当多个线程高频争用同一把锁（如 `std::mutex`）时，并发性能往往不仅停滞，甚至会随着线程数增加而出现反扩展（Scalability Collapse / Retrograde Scaling）。

---

当多个线程高频争用同一把锁（如 `std::mutex`）时，并发性能往往不仅停滞，甚至会随着线程数增加而出现**反扩展（Scalability Collapse / Retrograde Scaling）**。

## 锁竞争为何会破坏扩展性

- **串行化临界区（Serialization）**：互斥锁将原本可并行的代码段强制转为串行执行，受制于阿姆达尔定律（Amdahl's Law），共享临界区越长或争用越密，多核加速比上限越低。
- **缓存行乒乓（Cache Line Ping-Pong）**：锁状态变量（如 `futex` 字或自旋标志）通常位于单个 64 字节缓存行内。不同 CPU 核心上的线程反复读写该缓存行时，会触发 MESI/MOESI 一致性协议下的缓存行无效化与跨核传输，拉高单次获取/释放的延迟。
- **惊群与调度风暴**：大量线程同时阻塞在同一把锁上时，锁释放瞬间可能唤醒多个线程，但只有一个线程能真正拿到锁，其余线程再次失败并回到等待队列，白白消耗 CPU 周期与调度器资源。

## 临界区设计的基本原则

- **缩短持锁时间**：只在临界区内做必要的状态读写，把内存分配、日志 I/O、网络/磁盘请求、复杂计算和未知回调移出临界区。
- **降低锁粒度与避免嵌套加锁**：按独立数据分片加锁（如分段锁），严格规定全局加锁顺序，减少跨锁等待。
