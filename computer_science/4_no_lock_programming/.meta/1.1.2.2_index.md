# 1.1.2.2 为什么 C++ 中的 Data Race 是未定义行为（UB）？

很多刚接触无锁编程的开发者会认为：“Data Race 最多也就是读到旧值、少加几次，或者出现撕裂（Tearing）。”但在 C++ 标准中，Data Race 被定义为 **Undefined Behavior**，原因在于现代编译器与硬件架构的优化前提。

### 编译器的“无数据竞争假设”

现代优化编译器（如 GCC、Clang、MSVC）在生成机器码时，默认假设**源码中不存在数据竞争**。基于这一前提，编译器会执行大量合法的单线程等价变换：

* **寄存器提升与循环外提**：如果编译器认为循环体内某个共享变量不会被其他线程修改，可能把它缓存在寄存器中，甚至把读取提到循环外，导致其他线程的写入在循环里永远不可见（死循环或 stale 缓存）。
* **死存储消除与重排**：编译器可能合并、重排甚至消除看似多余的内存读写；一旦与另一个线程的无同步访问交错，就会出现违背直觉的观测结果。
* **非原子宽类型的撕裂（Tearing）**：对超过总线/缓存原子宽度或未对齐的对象进行非原子读写，可能拆分成多条指令执行，其他线程可能读到“一半旧值、一半新值”的拼凑状态。

### 硬件内存模型与缓存层次的影响

即便编译器不重排，多核 CPU 的写缓冲（Store Buffer）、无效化队列（Invalidate Queue）以及缓存一致性协议也会让“无同步并发读写”偏离直觉；而在 ARM64 等弱内存序架构上，缺少 `acquire` / `release` 等同步语义时，乱序观测的概率更高。

正因为同时涉及编译器优化与硬件内存序，C++ 标准选择把 Data Race 划入 UB，而不是规定某种“勉强能跑”的模糊行为——这赋予工具链优化空间，同时也要求开发者必须通过 `std::atomic`、互斥锁或不可变设计显式建立同步关系。
