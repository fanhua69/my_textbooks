# 1.1.1.07.4 PACELC：分布式系统中的一致性与延迟权衡

**介绍**: PACELC ：分布式系统中的一致性与延迟权衡

**PACELC** 是分布式系统中的一个重要理论，用来分析分布式数据库、缓存、消息系统以及微服务架构中的设计取舍。

它比 CAP 理论更进一步：不仅考虑网络分区发生时的取舍，也考虑网络正常时的一致性与延迟取舍。

## 1. PACELC 怎么读？

PACELC 是一个缩写，可以逐个字母读：

**P - A - C - E - L - C**

也有人把它近似读成 "Pack-Else-See"，但逐字母读最清楚。

它不是一个普通英语单词。

## 2. PACELC 是什么意思？

PACELC 描述两种不同情况下，分布式系统面临的权衡：

-   **P（Partition）**：发生网络分区（Network Partition）。
-   **A（Availability）**：可用性。
-   **C（Consistency）**：一致性。
-   **E（Else）**：否则，也就是没有发生网络分区。
-   **L（Latency）**：延迟。
-   **C（Consistency）**：一致性。

核心表达式：

\[
\boxed{P \rightarrow A/C,\quad E \rightarrow L/C}
\]


翻译成人话：

-   **发生网络分区时**：在可用性和一致性之间做权衡。
-   **没有发生网络分区时**：在延迟和一致性之间做权衡。

## 3. 第一种情况：发生网络分区（P）

假设有三个 Entitlement Server：

``` mermaid
flowchart TB
    subgraph N["正常网络"]
        A["Server A"] --- B["Server B"]
        B --- C["Server C"]
        A --- C
    end

    subgraph P1["Partition 1"]
        A2["Server A"]
        B2["Server B"]
        A2 --- B2
    end

    subgraph P2["Partition 2"]
        C2["Server C"]
    end

    P1 -. "网络分区：无法通信" .- P2
```

假设用户的权限刚刚被撤销：

-   Server A 已经收到更新。
-   Server B 已经收到更新。
-   Server C 因为网络分区，还不知道这个变化。

现在客户端向 Server C 查询权限。

### 选择 A：Availability（可用性）

Server C 继续使用本地缓存回答：

``` text
Client → Server C
             |
             v
        Local Cache
             |
             v
      Permission = ALLOW
```

优点：

-   服务继续运行。
-   查询延迟低。
-   不依赖远程节点。

缺点：

-   可能返回过期权限。
-   数据暂时不一致。

这是一种偏向 **AP** 的设计取向。

### 选择 B：Consistency（一致性）

Server C
无法确认自己的权限数据是否最新，于是拒绝、等待，或者将请求转发到能够确认状态的节点：

``` text
Client → Server C
             |
             v
       Cannot confirm
             |
             v
        Reject / Wait
```

优点：

-   避免使用无法确认的旧数据。
-   更容易维持强一致性要求。

缺点：

-   服务可能无法及时响应。
-   可用性下降。

这是一种偏向 **CP** 的设计取向。

> 注意：CAP 中的 C 通常指强一致性（常以
> Linearizability，即线性一致性来刻画），不是简单地说所有节点最终会同步。实际系统也可能采用超时、转发、只读降级等更细致的策略。

## 4. 第二种情况：没有网络分区（E）

这是 PACELC 比 CAP 更有意思的地方。

假设三个 Server 之间网络完全正常。

此时没有网络分区，但仍然存在一个问题：

**每次更新，是否需要等待其他节点确认？**

例如，用户修改权限：

``` text
Server A: Permission = DENY
```

### 方案一：优先低延迟（Latency）

Server A
更新本地数据后，立即返回；随后通过异步消息把更新传播给其他节点：

``` mermaid
flowchart TD
    Client["Client"] --> A["Server A"]
    A --> Cache["Update Local Cache"]
    Cache --> Reply["Return SUCCESS"]
    Cache --> MQ["Async Message Queue"]
    MQ --> B["Server B"]
    MQ --> C["Server C"]
```

优点：

-   响应快。
-   不需要等待其他节点。
-   通常有利于降低写入延迟。

缺点：

在消息传播完成之前，可能出现：

``` text
Server A: DENY
Server B: ALLOW
Server C: ALLOW
```

也就是短暂的数据不一致。

这是偏向 **EL**（Else + Latency）的设计取向。

### 方案二：优先一致性（Consistency）

Server A 更新后，等待其他节点或者满足指定的
quorum（法定人数）条件，再向客户端确认：

``` mermaid
flowchart TD
    Client["Client"] --> A["Server A"]
    A --> B["Server B：ACK"]
    A --> C["Server C：ACK"]
    B --> Q["满足确认条件"]
    C --> Q
    Q --> Reply["Return SUCCESS"]
```

优点：

-   可以提供更强的数据一致性保证。
-   减少不同节点之间的状态差异。

缺点：

-   增加网络通信。
-   增加响应延迟。
-   吞吐量可能下降。

这是偏向 **EC**（Else + Consistency）的设计取向。

> 等待所有节点确认只是一个简单示意。实际系统可以使用
> quorum、同步复制或其他一致性协议。是否真正满足线性一致性，取决于协议、读写路径和故障处理方式，不能仅凭"等待
> ACK"判断。

## 5. PACELC 的四种设计取向

把网络分区和正常运行两种情况组合起来：

  类型    网络分区时（P）   正常运行时（E）
  ------- ----------------- -----------------
  PA/EL   优先可用性        优先低延迟
  PA/EC   优先可用性        优先一致性
  PC/EL   优先一致性        优先低延迟
  PC/EC   优先一致性        优先一致性

这里的斜杠表示权衡方向，并不是说系统只能具备其中一项。

## 6. 联系 Bloomberg Entitlement

回到多 Entitlement Server 的架构假设：

-   有多个 Entitlement Server。
-   每个 Server 都有本地权限缓存。
-   使用 Message Queue 异步传播权限变更。
-   查询热路径尽量避免网络 I/O。

这种设计有一个明显特点：

### 正常运行时

**低延迟优先（偏向 EL）**

本地缓存直接查询，权限变更异步传播。查询不必等待其他节点，因此热路径延迟较低，但更新传播期间可能存在短暂不一致。

### 网络分区时

**可用性优先（偏向 PA）**

如果节点继续使用本地缓存提供查询服务，就能在网络分区期间维持服务，但需要接受缓存可能不是最新的风险。

因此，按照上述架构假设，它在设计取向上接近 **PA/EL**。

但是，这只是根据我们讨论的架构假设作出的分析，**不能据此断言 Bloomberg
实际采用
PA/EL**。要判断真实系统，需要了解它的复制协议、故障策略、权限撤销语义以及读写一致性保证。

### 权限授予和权限撤销，是否应该采用相同策略？

未必。

例如：

-   用户新获得某项权限，更新晚几毫秒生效，可能主要影响用户体验。
-   用户权限已经被撤销，但某个 Server 仍然返回
    `ALLOW`，可能造成严重的安全问题。

所以，高安全要求的权限系统可能对 **Revocation（权限撤销）**
采用更严格的策略，例如要求更强的确认机制、短期有效的授权凭证、版本校验或故障时拒绝授权。

这说明实际系统并不一定对所有操作采用同一种一致性策略。

## 7. CAP 和 PACELC 的区别

  理论     主要研究的问题
  -------- ----------------------------------------------------------
  CAP      网络分区发生时，如何权衡一致性和可用性？
  PACELC   网络分区时如何权衡？网络正常时，又如何权衡一致性和延迟？

记住这个公式：

\[ 
    \boxed{P \rightarrow A/C,\quad E \rightarrow L/C} 
\]

-   **P --- Partition**：网络分区。
-   **A --- Availability**：可用性。
-   **C --- Consistency**：一致性。
-   **E --- Else**：否则，即没有网络分区。
-   **L --- Latency**：延迟。

## 8. 核心结论

PACELC 最有价值的地方在于：

**即使网络完全正常，一致性也不是免费的。**

即使没有任何故障，你仍然需要在同步复制、跨节点通信、响应延迟和数据一致性之间作出工程取舍。

CAP 关注故障期间的取舍；PACELC
则提醒我们，正常运行期间也存在持续的取舍。
