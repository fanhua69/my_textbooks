# 1.1.1.10.03 事件重复（Duplicate Events）

**介绍**: 事件重复（Duplicate Events）

> **简介**：在分布式系统中，消费者可能已经完成处理，但 ACK 没有成功送达消息代理：

---

## 为什么会重复？

在分布式系统中，消费者可能已经完成处理，但 ACK 没有成功送达消息代理：

``` text
Consumer 收到 Event E
       |
       v
更新本地缓存成功
       |
       v
发送 ACK
       |
       X 网络断开，ACK 丢失
       |
       v
消息代理重新投递 Event E
```

消费者无法仅凭 ACK
丢失判断上一次处理是否成功，因此常见消息系统采用至少一次投递（At-least-once
Delivery）。

At-least-once
的含义是：消息可能被投递多次，但系统努力保证消息不会因为一次短暂故障就永久消失。

因此，消费者必须考虑重复事件。

## Idempotency（幂等性）

幂等（Idempotent）指：同一个操作执行一次或多次，最终效果相同。

数学上：

\[ f(f(x)) = f(x) \]

例如：

``` cpp
// 幂等：把权限状态设置为 revoked
void apply(const PermissionRevoked& event) {
    cache.set(event.user_id, event.security_id, Revoked);
}
```

无论执行一次还是三次，最终状态都是 Revoked。

相反，下面这种操作不是天然幂等的：

``` cpp
// 非幂等：每处理一次就递减
void apply(const PermissionRevoked& event) {
    --active_permission_count;
}
```

如果事件重复投递，计数器就会被多减。

更好的方式是使用事件携带的目标状态，或者在更新计数器时依据唯一事件 ID
做去重。

## Event ID 去重

每个事件都应有稳定且唯一的 ID：

``` text
event_id = evt-1001
```

消费者可以维护已处理事件集合：

``` sql
BEGIN;

INSERT INTO processed_events(event_id)
VALUES ('evt-1001');

-- 只有 event_id 首次插入成功时，才执行对应业务更新。

COMMIT;
```

在数据库消费者中，去重记录和业务更新应放在同一个事务里，否则可能出现"记录已去重，但业务更新没完成"或相反的故障窗口。

对于纯内存缓存消费者，可以采用：

-   有界去重窗口（Deduplication Window）。
-   每个分区的最后处理 offset。
-   每个实体的最新版本号。
-   可恢复的消费 checkpoint。

不要无限保存所有 event ID，否则去重集合本身会无限增长。

## 权限同步中更实用的策略：状态设置优于状态累加

如果事件表达的是状态：

``` text
PermissionGranted(user=A, resource=X, version=10)
PermissionRevoked(user=A, resource=X, version=11)
```

消费者应尽量把事件解释为"将实体设置为某个版本的状态"，而不是"执行一次增量动作"。

这会让重复处理更容易变成幂等操作。

但仅靠幂等还不够：如果旧事件在新事件之后到达，仍可能把状态覆盖回旧值。这就引出事件乱序问题。
