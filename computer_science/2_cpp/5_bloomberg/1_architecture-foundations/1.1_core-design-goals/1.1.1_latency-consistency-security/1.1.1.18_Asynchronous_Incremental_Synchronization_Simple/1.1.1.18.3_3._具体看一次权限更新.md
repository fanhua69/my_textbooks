# 1.1.1.18.3 **3. 具体看一次权限更新**

**介绍**: **3. 具体看一次权限更新**

> **简介**：假设当前内存快照是 Version 100。

---

假设当前内存快照是 Version 100。

**Version 100：原始快照**

| User ID | Permissions        |
| ------- | ------------------ |
| 1001    | Bloomberg, Reuters |
| 1002    | Bloomberg, NASDAQ  |
| 1003    | Reuters, NYSE      |

Event

**User 1001 获得 CME 权限**

**Version 101：新快照**

| User ID | Permissions             |
| ------- | ----------------------- |
| 1001    | Bloomberg, Reuters, CME |
| 1002    | Bloomberg, NASDAQ       |
| 1003    | Reuters, NYSE           |

只有 User 1001 的数据发生变化。

实际过程如下：

**Step 1：数据库提交变更**

```
INSERT INTO user_permissions
    (user_id, permission)
VALUES
    (1001, 'CME');
```

数据库提交成功后，产生一条变更事件：

```
struct PermissionEvent {
    UserId user_id;
    PermissionId permission_id;
    uint64_t version;
    Operation operation;
};
```

例如：

```
user_id       = 1001
permission_id = CME
version       = 101
operation     = GRANT
```

**Step 2：后台线程接收事件**

事件可以通过以下机制传递：

- Message Queue：消息队列。
- Pub/Sub：发布订阅。
- CDC（Change Data Capture）：数据库变更捕获。
- Transactional Outbox：事务性发件箱。

后台 Worker 收到事件后，开始更新本地数据。

**Step 3：构建新快照**

后台线程不能直接修改正在被查询线程读取的快照。

因此，采用 Copy-on-Write（写时复制）思想：

```
auto new_snapshot =
    std::make_shared<Snapshot>(*old_snapshot);

new_snapshot->grant(1001, CME);
```

此时：

- `old_snapshot` 不变。
- `new_snapshot` 包含最新权限。
- 读线程仍然可以继续读取旧快照。

**Step 4：原子发布新快照**

```
std::atomic_store(
    &current_snapshot,
    new_snapshot
);
```

这一步非常关键。

新快照构建完成后，通过原子操作替换当前快照。

从此以后，新查询线程就能看到 Version 101。
