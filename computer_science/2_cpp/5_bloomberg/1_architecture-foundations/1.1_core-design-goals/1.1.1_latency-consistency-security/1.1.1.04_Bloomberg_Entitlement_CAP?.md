# 1.1.1.04 Bloomberg_Entitlement_CAP?

**介绍**: Bloomberg_Entitlement_CAP?

---
我查了一下。这个问题很有意思，因为 Bloomberg 的 Entitlement 正好涉及我们前面讨论的三个核心问题：

- **Low Latency**：权限检查不能成为行情分发链路的瓶颈。
- **High Availability**：纽约、伦敦、东京等地的服务不能轻易因为网络故障而停止工作。
- **Security**：用户的权限被撤销后，不能继续无限期地使用旧权限。

先说结论：

**目前没有找到 Bloomberg 官方公开资料明确宣布其 Entitlement 系统采用 AP 或 CP。** 因此，不能严谨地断言 Bloomberg 是 AP 或 CP。

但是，Bloomberg 公开的 API 文档和工程资料，确实能让我们分析它的设计方向。

## **1. Bloomberg 官方 API 暴露了一个重要事实：本地权限缓存**

我找到了一份很有价值的官方文档：

[Bloomberg BLPAPI – SendAuthorizationRequest](https://bloomberg.github.io/blpapi-docs/dotnet/3.25.1/html/M_Bloomberglp_Blpapi_AbstractSession_SendAuthorizationRequest_3.htm?utm_source=chatgpt.com)。

其中第 120 行明确写道：

> If a user is successfully authorized all the entitlements for that user is cached locally.

意思是：

**用户授权成功后，该用户的全部 entitlement 会被本地缓存。**

这意味着至少在 BLPAPI 的客户端权限模型中：

1. 首先向 Authorization Service 发起授权请求。
2. 授权成功后，获得用户的 Identity。
3. 用户的 entitlement 被缓存。
4. 后续可以使用这个 Identity 进行本地权限检查。

另外，Bloomberg 的 C++ API 也提供：

```
identity.hasEntitlements(
    service,
    entitlementIds,
    numEntitlements
);
```

这个接口直接检查 Identity 中的权限，不要求调用者每次都重新发起远程授权请求。

参考：[Bloomberg BLPAPI C++ Identity Class](https://bloomberg.github.io/blpapi-docs/cpp/3.22/classBloombergLP_1_1blpapi_1_1Identity.html?utm_source=chatgpt.com)。



已证实

&#x20;Bloomberg 的公开 API 确实支持本地缓存和本地 entitlement 检查。



但注意：这并不能证明纽约、伦敦、东京的后台服务器之间采用 AP 复制策略。

## **2. Bloomberg 的架构更可能是分层设计**

还有一份 Bloomberg 2026 年的工程招聘资料，介绍了 Login Platform：

[Bloomberg – Senior Software Engineer, Login Platform](https://jobs.anitab.org/companies/bloomberg/jobs/84363206-senior-software-engineer-login-platform?utm_source=chatgpt.com)。

其中提到：

- Sessions 是 Bloomberg 授权决策的基础。
- Session 携带 entitlements、customer data 和 security context。
- 这些信息会在 Bloomberg 的不同系统之间传播。

另外，Bloomberg 的招聘资料还明确提到了 Centralized Entitlement Platform。

这说明 Bloomberg 的权限体系涉及集中式权限基础设施和分布式授权上下文，而不是简单地每次查询都访问一个中央数据库。

参考：[Bloomberg – Analytics Platform Engineering](https://jobs.anitab.org/companies/bloomberg/jobs/87420830-senior-software-engineer-analytics-platform?utm_source=chatgpt.com)。

## **3. 如果让我推测 Bloomberg 的 CAP 设计**

下面是我的工程推断，不是 Bloomberg 已公开证实的内部实现。

我认为比较合理的架构是：

**Control Plane（权限控制面）**

**Central Entitlement Service**

权限修改、授权、撤销、版本管理

**New York**

Local Cache

Read

**London**

Local Cache

Read

**Tokyo**

Local Cache

Read

**Data Plane（权限查询数据面）**

**Local Entitlement Check**

本地内存查询、无远程 I/O、低延迟

**hasEntitlements() → O(1) / O(n)**

这是用于解释设计思路的示意图，不代表 Bloomberg 已披露的真实架构。

我会考虑采用以下策略：

| 操作          | 倾向                  | 原因             |
| ----------- | ------------------- | -------------- |
| 已授权用户读取权限   | AP 倾向               | 使用本地缓存，保证低延迟   |
| 新增权限        | 有条件传播               | 避免权限传播不一致      |
| 撤销权限        | CP / Fail-Closed 倾向 | 避免撤销后继续非法访问    |
| 网络分区期间的新授权  | CP 倾向               | 无法确认权限时拒绝授权    |
| 网络分区期间的已有授权 | 视策略而定               | 需要考虑缓存有效期和撤销延迟 |

这里尤其要注意：新增权限和撤销权限的安全影响并不对称。

- 新增权限传播慢：用户暂时无法访问本来有权访问的数据。
- 撤销权限传播慢：用户可能继续访问已经无权访问的数据。

后者通常更严重。

## **4. 我的最终判断**

尚无公开证据确认

我不会把 Bloomberg Entitlement 简单归类为 AP 或 CP。

更准确的描述是：

**Bloomberg 的公开 API 体现了本地缓存和低延迟权限检查的设计；其后台权限数据的复制、一致性协议、网络分区策略以及撤销传播机制，没有足够的公开资料可以确认。**

如果你正在编写自己的 Entitlement 教材，我建议把这一节改成：

> Bloomberg Entitlement 可以作为分布式权限系统的工程案例，但不能据其本地缓存机制直接断言它采用 AP。一个合理的设计方向是：权限读取走本地缓存，权限变更通过分布式同步传播，对权限撤销采用更严格的一致性和失效策略。

**还有一个我认为值得深入研究的问题：**

对于 Bloomberg 这种每秒处理海量行情消息的系统，假设一个用户刚刚被撤销了某项行情权限，如何让全球数百个分发节点尽快停止向这个用户发送数据，同时又不在每条行情消息上增加一次远程权限查询？

这才是 Entitlement 真正困难的 Low Latency + Distributed Consistency 问题。
