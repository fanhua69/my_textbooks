# 1.1.1.11 Asynchronous Incremental Synchronization

**介绍**: As

# **异步增量同步（Asynchronous Incremental Synchronization）**

这是高性能权限系统中非常重要的一种架构设计。

它的核心思想是：

**数据库发生变化时，不立即让所有查询线程更新数据，而是由后台线程异步获取变化，只更新发生变化的部分，然后发布给查询线程使用。**

我们从一个 Bloomberg Entitlement（权限管理）系统的例子来理解。

## **1. 为什么需要异步增量同步？**

假设系统有 100 万个用户，每个用户有若干权限。

内存中维护一份权限索引：

```
UserId -> Permissions
```

例如：

```
User 1001 -> {Bloomberg, Reuters, NYSE}
User 1002 -> {Bloomberg, NASDAQ}
User 1003 -> {Reuters, NYSE}
...
```

现在，User 1001 新增了一项权限：

```
User 1001 -> {Bloomberg, Reuters, NYSE, CME}
```

最简单的做法是：

1. 从数据库读取最新数据。
2. 更新内存中的权限索引。
3. 通知所有查询线程。

但如果每次权限发生变化，都重新加载 100 万个用户的数据，成本就很高。

这就是为什么要采用 **Incremental Synchronization（增量同步）**。

只同步发生变化的数据，而不是全部数据。

可以把系统分成三个部分：

- **Persistent Storage（持久化存储）**：保存权威权限数据。
- **Background Synchronization Worker（后台同步线程）**：获取变化、构建新索引。
- **Read Path（查询路径）**：只读取内存快照。

整体流程：

```
              ┌──────────────────────┐
              │   Persistent Storage │
              │      Database        │
              └──────────┬───────────┘
                         │
                    权限发生变化
                         │
                         ▼
              ┌──────────────────────┐
              │   Change Event       │
              │  User 1001: Grant CME│
              └──────────┬───────────┘
                         │
                    异步传递
                         │
                         ▼
              ┌──────────────────────┐
              │ Background Worker    │
              │                      │
              │ 1. 接收变化事件       │
              │ 2. 更新内存索引       │
              │ 3. 构建新 Snapshot   │
              └──────────┬───────────┘
                         │
                    原子发布
                         │
                         ▼
              ┌──────────────────────┐
              │   Atomic Snapshot    │
              │                      │
              │    Version 102       │
              └──────────┬───────────┘
                         │
                 多个查询线程读取
                ┌────────┼────────┐
                ▼        ▼        ▼
              Reader1  Reader2  Reader3
```

这里有两个关键概念：

- Asynchronous：异步，更新操作不阻塞在线查询线程。
- Incremental：增量，只处理发生变化的数据。

两者结合起来，就是后台异步处理变化，前台继续使用现有数据。

## **3. 具体看一次权限更新**

假设当前内存快照是 Version 100。

**Version 100：原始快照**

| User ID | Permissions        |
| ------- | ------------------ |
| 1001    | Bloomberg, Reuters |
| 1002    | Bloomberg, NASDAQ  |
| 1003    | Reuters, NYSE      |

Event

**User 1001 获得 CME 权限**

**Version 101：新快照**

| User ID | Permissions             |
| ------- | ----------------------- |
| 1001    | Bloomberg, Reuters, CME |
| 1002    | Bloomberg, NASDAQ       |
| 1003    | Reuters, NYSE           |

只有 User 1001 的数据发生变化。

实际过程如下：

**Step 1：数据库提交变更**

```
INSERT INTO user_permissions
    (user_id, permission)
VALUES
    (1001, 'CME');
```

数据库提交成功后，产生一条变更事件：

```
struct PermissionEvent {
    UserId user_id;
    PermissionId permission_id;
    uint64_t version;
    Operation operation;
};
```

例如：

```
user_id       = 1001
permission_id = CME
version       = 101
operation     = GRANT
```

**Step 2：后台线程接收事件**

事件可以通过以下机制传递：

- Message Queue：消息队列。
- Pub/Sub：发布订阅。
- CDC（Change Data Capture）：数据库变更捕获。
- Transactional Outbox：事务性发件箱。

后台 Worker 收到事件后，开始更新本地数据。

**Step 3：构建新快照**

后台线程不能直接修改正在被查询线程读取的快照。

因此，采用 Copy-on-Write（写时复制）思想：

```
auto new_snapshot =
    std::make_shared<Snapshot>(*old_snapshot);

new_snapshot->grant(1001, CME);
```

此时：

- `old_snapshot` 不变。
- `new_snapshot` 包含最新权限。
- 读线程仍然可以继续读取旧快照。

**Step 4：原子发布新快照**

```
std::atomic_store(
    &current_snapshot,
    new_snapshot
);
```

这一步非常关键。

新快照构建完成后，通过原子操作替换当前快照。

从此以后，新查询线程就能看到 Version 101。

## **4. 为什么不能直接修改原来的 Snapshot？**

假设有三个查询线程：

```
Thread 1 ──┐
Thread 2 ──┼──> Snapshot Version 100
Thread 3 ──┘
```

后台线程正在修改 User 1001 的权限。

如果直接修改：

```
snapshot.grant(1001, CME);
```

就可能出现：

- Thread 1 读取到了旧权限。
- Thread 2 读取到了更新一半的数据。
- Thread 3 读取到了新权限。

这会造成并发数据竞争，甚至导致查询结果不一致。

采用不可变快照：

```
                  ┌─────────────────┐
                  │ Snapshot V100   │
                  │ 只读            │
                  └─────────────────┘
                          ▲
                          │
             Reader 1, 2, 3
                          │

Background Worker
       │
       ▼
  构建 Snapshot V101
       │
       ▼
  Atomic Pointer Swap
       │
       ▼
                  ┌─────────────────┐
                  │ Snapshot V101   │
                  │ 只读            │
                  └─────────────────┘
```

这样，查询线程永远不会看到正在被修改的快照。

注意：原子指针切换保证的是发布过程的原子性，并不意味着所有查询线程在同一时刻切换。已经持有 V100 的查询线程可以继续完成查询。

## **5. C++17 如何实现？**

先看一个简化版本。

```
#include <memory>
#include <atomic>
#include <unordered_map>
#include <vector>

using UserId = uint64_t;
using PermissionId = uint32_t;

struct Snapshot {
    uint64_t version;

    std::unordered_map<
        UserId,
        std::vector<PermissionId>
    > permissions;

    bool has_permission(
        UserId user,
        PermissionId permission
    ) const {
        auto it = permissions.find(user);

        if (it == permissions.end())
            return false;

        const auto& list = it->second;

        return std::find(
            list.begin(), list.end(), permission
        ) != list.end();
    }
};

// 当前快照
std::shared_ptr<const Snapshot> current_snapshot;
```

### **Reader：查询线程**

```
bool check_permission(
    UserId user,
    PermissionId permission
) {
    auto snapshot =
        std::atomic_load(&current_snapshot);

    return snapshot->has_permission(
        user, permission
    );
}
```

查询线程做三件事：

1. 原子获取当前 Snapshot。
2. 在内存中查找权限。
3. 返回结果。

它不需要获取业务互斥锁，也不访问数据库。

### **Writer：后台同步线程**

```
void apply_event(const PermissionEvent& event)
{
    auto old_snapshot =
        std::atomic_load(&current_snapshot);

    auto new_snapshot =
        std::make_shared<Snapshot>(*old_snapshot);

    // 修改新快照
    new_snapshot->version = event.version;

    // 根据 event.operation 更新权限
    apply_permission_change(
        *new_snapshot, event
    );

    // 原子发布
    std::atomic_store(
        &current_snapshot,
        std::shared_ptr<const Snapshot>(
            new_snapshot
        )
    );
}
```

这里有一个重要的 C++ 知识点：

`std::atomic_load()` 和 `std::atomic_store()` 对 `shared_ptr` 的支持从 C++11 就有了。

它们是针对 `shared_ptr` 的原子操作自由函数（Atomic Shared Pointer Operations），不是普通的 `shared_ptr` 成员函数。

C++20 才正式提供：

```
std::atomic<std::shared_ptr<T>>
```

另外，这里的代码是教学示意，省略了初始化、事件排序和异常处理。

## **6. 真正的工程难点在哪里？**

上面的代码看起来很简单，但实际生产系统还需要解决几个重要问题。

| 问题       | 解决思路                                   |
| -------- | -------------------------------------- |
| 事件丢失     | Durable Message Queue、CDC              |
| 事件重复     | Idempotency（幂等处理）                      |
| 事件乱序     | Sequence Number、Version                |
| 后台线程崩溃   | Checkpoint、Replay                      |
| 同步通道断开   | Full Resynchronization                 |
| 快照过旧     | Version Monitoring、Fail-Closed         |
| 快照复制成本太高 | Sharding、Persistent Data Structure、RCU |

特别注意一个容易忽略的问题：

```
auto new_snapshot =
    std::make_shared<Snapshot>(*old_snapshot);
```

这实际上可能复制整个 `unordered_map`。

即使只修改了一个用户，也可能需要 O(N) 的复制成本。

所以，真正的低延迟系统通常还需要进一步优化：

- 按用户分片（Sharding）。
- 只复制发生变化的分片。
- 使用不可变节点和结构共享（Structural Sharing）。
- 使用 RCU（Read-Copy-Update）等技术管理读写和对象生命周期。

这些才是后续深入 C++ 无锁编程时值得研究的内容。

## **7. 还有一个非常重要的问题：如何保证事件不丢？**

假设数据库已经提交了 Version 101，但后台同步线程突然崩溃。

此时：

```
Database Version: 101
Memory Snapshot:  100
```

如果系统没有恢复机制，内存权限就会一直落后。

因此，通常会维护：

```
struct SyncStatus {
    uint64_t database_version;
    uint64_t snapshot_version;
};
```

监控：

```
Replication Lag =
    database_version - snapshot_version
```

恢复机制通常包括：

1. 持久化事件日志。
2. 记录最后处理的事件序列号。
3. 后台线程重启后从 Checkpoint 恢复。
4. 如果无法确定数据完整性，重新加载完整快照。
