# 1.1.1.08.6 C++17 快照并发安全读取与发布：选型建议

**介绍**: C++17 快照并发安全读取与发布：选型建议

在 C++17 里，标准库还没有提供 std::atomic<std::shared_ptr<T>>（那是 C++20 才加进来的），而且 C++11/17 中那组老式的 std::atomic_load / std::atomic_store 自由函数在 C++20 已经被标记为废弃（deprecated），同时在部分编译器/实现下存在性能或内存序细节问题。

在 C++17 中实现“快照整份发布 + 读线程不与写线程互斥”，主要有 3 种常见方案，按工程实践程度从推荐到备选排列：

## 方案一：写侧加互斥锁（std::mutex）+ 读侧短临界区拷贝 shared_ptr（最稳妥、最推荐）

核心思想：
在线读线程只用 std::mutex 保护“拷贝 std::shared_ptr 指针本身”这几纳秒的操作，拿到局部 shared_ptr 后立刻解锁，后续查哈希表完全在锁外进行。
这样：

读线程之间不互相阻塞；

读线程拿到 shared_ptr 后，即使后台写线程换了新快照并释放旧快照，读线程手里的旧快照也依然存活（引用计数大于 0）；

读线程不会与耗时的“构建新快照 / 写业务”互相长久阻塞（锁粒度极小，仅指针拷贝）。

注意：C++17 下对同一个 std::shared_ptr 变量，一线程写、另一线程读，必须同步；用 std::mutex 保护那一次 shared_ptr 拷贝是最清晰、不易踩坑的做法。

## 方案二：C++11/17 标准库自由函数 std::atomic_load / std::atomic_store

C++11 引入了针对 std::shared_ptr 的原子自由函数（位于 <memory>）：

读：std::atomic_load_explicit(&ptr, std::memory_order_acquire)

写：std::atomic_store_explicit(&ptr, new_ptr, std::memory_order_release)

为什么很多低延迟团队在 C++17 不首选它？

不少标准库实现内部是用全局哈希表 + 自旋锁/互斥锁模拟 shared_ptr 原子的，存在锁竞争热点和实现差异；

到了 C++20 这组自由函数被正式 deprecated，未来升级标准时要改代码。

因此在绝大多数业务和系统服务里，方案一（std::mutex 仅包一层 shared_ptr 指针拷贝）往往比盲目用 std::atomic_load(&shared_ptr) 更可控、更易读。


方案三：极致低延迟场景——裸指针/控制块 + 延迟回收（Hazard Pointer / Epoch / RCU 思路）
如果连 std::mutex 拷贝 shared_ptr 的原子引用计数开销都不想承受，可以把 PermissionSnapshot 堆对象指针用 std::atomic<const PermissionSnapshot*> 发布，但必须解决“何时安全 delete 旧快照”的问题：

常见做法：

延迟回收队列 / Epoch（纪元）回收：记录当前活跃读者的最小 epoch，只有当所有读线程都离开旧快照对应的 epoch 后，再由后台线程回收旧快照内存；

或直接引入成熟库（如 Folly AtomicSharedPtr、RCU 实现），避免自己手写内存回收时出现 ABA 或过早释放。


在“异步同步线程 / Consumer 定期构建新快照 + 在线请求线程读取最新快照”的架构中，核心诉求是：**写侧发布新快照时，读线程既不会读到改了一半的“撕裂状态”，也不会在读取过程中遇到对象被提前销毁的悬垂指针**。

由于 C++17 标准库尚未提供 `std::atomic<std::shared_ptr<T>>`（该特性在 C++20 引入），在 C++17 下通常根据业务并发量、延迟敏感度和维护成本选择不同方案。

## 选型对比总览

| 场景 | C++17 推荐做法 | 特点 |
| :--- | :--- | :--- |
| 常规在线鉴权 / 配置快照 | `std::mutex` 仅保护 `shared_ptr` 指针赋值与拷贝 | 代码简单、零数据竞争、生命周期由 `shared_ptr` 自动管理 |
| 存量 C++11/17 代码快速落地 | `std::atomic_load_explicit` / `std::atomic_store_explicit` | 无需额外锁，但注意 C++20 已废弃及实现差异 |
| 纳秒级压榨 / 超高频读写 | 原子原始指针 + Epoch / RCU / 成熟库 | 避免 `shared_ptr` 引用计数争用，但回收机制复杂 |

---

## 1. 常规在线鉴权 / 配置快照

* **C++17 推荐做法：** `std::mutex` 仅保护 `shared_ptr` 指针赋值与拷贝。
* **核心思路：**
  * 写侧（异步同步线程 / Consumer）在锁外构造完整的不可变新快照对象，仅在替换当前 `shared_ptr` 指针时短暂加锁。
  * 读侧（在线请求线程）仅在极短临界区内拷贝一份局部 `shared_ptr` 副本并立即解锁，后续遍历和查询完全在锁外执行。
* **特点与权衡：**
  * **优点：** 逻辑直观、不易出错、无数据竞争；读线程拿到局部 `shared_ptr` 后，即使后台发布新快照并释放旧指针，旧快照也会在引用计数归零前安全存活。
  * **注意：** 锁的粒度必须严格控制在“指针拷贝/赋值”这一步，切勿把快照深拷贝或业务查询逻辑放进锁内。

## 2. 存量 C++11/17 代码快速落地

* **C++17 推荐做法：** `std::atomic_load_explicit` / `std::atomic_store_explicit`（针对 `std::shared_ptr`）。
* **核心思路：**
  * 利用 `<memory>` 中针对 `std::shared_ptr` 的原子自由函数，通过 `std::memory_order_acquire` 读取快照副本、`std::memory_order_release` 发布新快照。
* **特点与权衡：**
  * **优点：** 无需在业务类中显式维护 `std::mutex`，适合在已有 C++11/17 代码基础上快速接入。
  * **注意：** 该组自由函数在 C++20 中已被标记为废弃（deprecated），后续升级标准时可能需要重构；此外不同标准库实现的底层同步机制存在差异，极端高并发下需实测其争用表现。

## 3. 纳秒级压榨 / 超高频读写

* **C++17 推荐做法：** 原子原始指针 + Epoch / RCU / 成熟库。
* **核心思路：**
  * 当在线读线程极多、连 `shared_ptr` 拷贝时的原子引用计数增减（`fetch_add` / `fetch_sub`）都成为缓存行（Cache Line）争用瓶颈时，可改用 `std::atomic<const Snapshot*>` 发布指针，并结合 Epoch（纪元）回收、RCU（Read-Copy-Update）或业界成熟并发组件（如 Folly 等）来安全回收旧快照。
* **特点与权衡：**
  * **优点：** 读路径开销极低，避免引用计数带来的原子指令争用，适合高吞吐、低延迟敏感的系统。
  * **注意：** 内存回收时机判断复杂，自行实现容易出现过早释放或回收滞后导致内存增长，优先建议复用成熟库而非手写轮子。

---

## 4. 落地决策建议

1. **默认优先选第一种（`std::mutex` 仅包一层 `shared_ptr` 指针拷贝）：** 绝大多数在线权限校验、配置下发与读多写少快照场景，可读性与可维护性远高于微小的同步开销。
2. **明确性能瓶颈后再升级到第三种：** 只有当压测或性能剖析（Profiler）明确显示 `shared_ptr` 引用计数争用成为瓶颈时，再引入 Epoch / RCU 或成熟并发库。
