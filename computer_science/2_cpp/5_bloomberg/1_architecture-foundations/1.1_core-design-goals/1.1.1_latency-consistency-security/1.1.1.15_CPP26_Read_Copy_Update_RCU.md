# 1.1.1.15 CPP26_Read_Copy_Update_RCU

**介绍**: CPP26_Read_Copy_Update_RCU

---

* C++26 引入了 RCU（Read-Copy-Update，读-拷贝-更新） 标准库支持（源自提案 P2545），与风险指针（Hazard Pointers）一起归入“安全回收（Safe reclamation）”机制。

* 它把原本在 Linux 内核和用户态库（如 liburcu、Folly）中广泛使用的并发模式带入了 ISO C++ 标准库，专门针对读多写少（read-mostly）的并发数据结构。

## 1. RCU 的核心思路与优势

* 传统读写锁（std::shared_mutex）在超高并发读取时，即使没有写者，读线程频繁修改共享状态或缓存行也会带来竞争和 Cache Line 颠簸（Cache-line bouncing）。

* RCU 换了一种方式：

* 无锁/极低开销读端： 读线程进入 RCU 保护区（lock() / unlock()）后可直接读取共享数据，不会被写者阻塞，也不需要等待其他读线程。

* 先拷贝再更新（Copy-Update）：
写者修改数据时不直接原地覆盖旧节点，而是分配并构造新副本，随后通过原子指针替换让新读线程看到新数据。

**宽限期（Grace Period）与延迟回收：**

指针替换完成后，旧节点可能仍被“替换前已进入读区”的线程持有。
RCU 等待所有旧读者都离开保护区（经过一个宽限期），再安全销毁或回收旧对象。

## 2. C++26 RCU 的核心接口

C++26 的 RCU 围绕域（domain）、可保护对象基类以及同步/回收原语构建：

std::rcu_domain 与 std::rcu_default_domain()： 表示一个 RCU 保护域。通过 lock() 和 unlock()（可嵌套，也可配合 RAII 守卫使用）划定读端临界区。

std::rcu_obj_base： 侵入式（intrusive）辅助基类，让对象类型具备 RCU 回收所需的元数据支持；同时也支持非侵入式/自定义回收路径。

std::rcu_synchronize()： 阻塞当前写线程，直到当前域中所有已有的 RCU 读临界区结束（即等待一个宽限期完成）。

std::rcu_retire(...)： 提交延迟销毁/回收任务。在宽限期结束后执行指定的清理或析构逻辑，避免写线程在热路径上死等。

std::rcu_barrier()： 阻塞等待此前所有已排队的 rcu_retire 回调/回收操作执行完毕（常用于优雅退出或测试清理）。

3. 适用场景与使用陷阱
最适合的场景：

路由表、配置快照、特性开关、注册表、读多写少的无锁链表/树结构。

读吞吐量极高、写操作相对稀疏，且无法承受读写锁争用的系统。

使用时的关键注意事项：

不要在 RCU 读临界区内做阻塞操作： 读区越短、越纯粹，宽限期推进越快；在读区内长时间睡眠或等待锁会延迟内存回收甚至导致阻塞。

注意回调/析构函数中的锁顺序： rcu_retire 的清理逻辑可能在后台线程或特定时机执行，若在 deleter 中无条件获取外部互斥锁，容易引发死锁。

关注程序退出时的生命周期： 进程或静态存储期对象析构阶段，需确保不再提交新的 rcu_retire 并通过 rcu_barrier() 等机制妥善收尾，避免悬垂访问。

对比 Hazard Pointers： RCU 适合读端成批推进、按宽限期批量回收的“读多写少”结构；若更倾向于逐个指针精确记录引用、写频率更高或结构访问模式不同，Hazard Pointers 往往是另一条重要补充路线。
