# 1.1.1.02 Fail_Closed 安全降级是啥意思

**介绍**: 安全降级（Fail-Closed） 是啥意思

安全降级（Fail-Closed）是指系统、组件或检查机制在遇到故障、超时、异常或依赖不可用时，默认拒绝请求或阻断操作，宁可“关门/拒绝”，也不在状态不确定的情况下放行。

它的核心理念是：安全优先于可用性（Safety / Security over Availability）。与之相对的是 Fail-Open（故障开放 / 放行降级），即出错时默认放行，优先保证业务可用。

## 工作机制与典型场景

当某个校验或控制环节无法正常工作时，Fail-Closed 的执行路径通常是：

触发异常：鉴权服务超时、权限缓存失效、风控引擎报错或硬件安全模块无响应。

拒绝放行：不猜测结果、不走“默认允许”兜底，直接返回拒绝（如 403 / 503、阻断连接或停止动作）。

记录与告警：记录错误日志与指标，触发监控告警，等待依赖恢复。

## 常见工程与物理场景

身份认证与权限校验（AuthN / AuthZ）：Token 校验服务或权限中心宕机时，直接拒绝访问受保护资源，而不是把所有请求当成“已授权”。
风控与反欺诈（Risk / Fraud Control）：交易或下单时若风控规则引擎超时不可用，高风险场景下直接拦截或要求二次验证，避免资金损失。
安全门禁与工业控制：电子门锁断电或控制器故障时保持锁定状态（常闭锁），或关键阀门在控制信号丢失时自动关闭以防止泄漏。

# Fail-Closed 与 Fail-Open 对比

维度|Fail-Closed（安全降级）|Fail-Open（放行降级）
-|-|-
故障时默认行为|拒绝 / 阻断 / 锁定|放行 / 降级跳过检查
首要保护目标|安全性、合规性、资金与数据完整|可用性、吞吐量、用户体验
主要风险|依赖故障可能引发误拦截或业务不可用|依赖故障可能导致越权、攻击或脏数据流入
典型适用点|登录鉴权、支付风控、密钥校验、门禁|非敏感推荐、次要埋点/日志、部分读缓存



## 工程实践中的权衡

在真实系统设计中，很少把整个系统一刀切设为 Fail-Closed，而是按风险等级分层：
核心资产与安全边界（如账户权限、支付扣款、敏感配置修改）通常采用 Fail-Closed。
非关键体验路径（如个性化推荐、非核心统计上报）往往采用 Fail-Open 或本地静态兜底，避免上游抖动拖垮整个前端。
关键防线：如果使用 Fail-Closed，必须配合高可用部署、超时控制、健康检查与快速恢复预案，否则一旦依赖服务长时间故障，就会变成大面积服务中断。

## 为什么叫安全”降级“？

之所以叫“降级”（Degradation），是因为系统在依赖异常或资源受限时，放弃了原本“完整校验并正常放行/提供全量服务”的标准工作模式，转入一种“受限/收缩的兜底状态”；而加上“安全”二字，说明这种收缩是向着更保守、更安全的方向收缩，而不是向着“放宽限制、凑合放行”的方向收缩。

## “降级”在这里到底降了什么？

很多人看到“降级”会下意识以为是“功能变弱、凑合用”，但在系统工程里，“降级”的核心含义是脱离常规完整路径，进入有限状态机中的非正常分支。对 Fail-Closed（安全降级） 来说，降掉的主要是这两样：
降掉“正常业务放行能力”：在正常状态下，请求经过校验后会被放行完成业务；当校验依赖不可用时，系统不再尝试完成完整业务放行，而是降级为“一律拒绝/阻断”。对外部调用方来说，服务能力明显收缩了，所以叫“降级”。
降掉“动态实时计算/校验路径”：有时系统不会简单粗暴地全拒，而是放弃实时远程校验，降级为使用本地已知的安全规则、只读模式或保守阈值（例如只允许高可信/白名单操作，或直接关闭高风险写操作）。

## 为什么容易产生误解？

日常聊“服务降级”，人们最常想到的是可用性降级（如 Fail-Open 或功能开关降级）——比如大促时关掉评论、推荐，或者缓存查不到/鉴权超时就先放行，保住核心下单流程。
可用性导向的降级：遇到故障时，降低安全/一致性/完整性要求，保住“能用、能通”。
安全导向的降级（Fail-Closed）：遇到故障时，降低“放行/可用性”指标，保住“不出错、不越权、不丢钱”。
两者都属于“系统遇到异常时主动改变运行策略（降级）”，只是牺牲的维度相反。如果只看“系统是否还能正常响应业务请求”，Fail-Closed 确实是把业务处理能力“降”到了拒绝态；但从风险控制角度看，它是把风险敞口降到了最低，因此中文常译作“安全降级”。

一句话总结
这里的“降级”指的是系统从“正常放行服务”退守到“拒绝/锁定保守状态”，而不是“降低安全标准”。
