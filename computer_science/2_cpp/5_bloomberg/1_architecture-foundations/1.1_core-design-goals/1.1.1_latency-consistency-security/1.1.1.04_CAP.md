# 1.1.1.04 CAP

**介绍**: CAP

这个问题问得非常好。实际上，这正是 CAP 定理最容易让人困惑的地方。

你的疑问是：

**既然 Network Partition 意味着服务器之间无法通信，为什么系统还能保证 Availability？**

关键在于：

**Partition 不等于服务器全部瘫痪，而是服务器之间的网络通信发生了故障。**

## **1. 看一个具体场景**

假设有三个节点：

**Node A**

Online

**Node B**

Online

**Node C**

Online

**Network Partition**

A、B 与 C 之间的通信中断

**Partition 1**

A + B

**Partition 2**

C

三个节点仍然运行，只是分成两个无法互相通信的网络分区。

现在用户分别访问 A、B、C。

三个节点都能收到客户端请求。

问题是：它们无法互相交换数据。

## **2. AP：选择 Availability**

假设原来的数据是：

```
Account Balance = $1000
```

发生网络分区后：

- 用户向 A 存入 $100，A 更新为 $1100。
- 用户向 C 取出 $200，C 更新为 $800。

A 和 C 都继续接受请求。

它们都能返回成功响应。

这就是 Availability。

但是：

```
Node A: $1100
Node B: $1000
Node C: $800
```

数据已经不一致了。

等网络恢复后，需要进行数据协调（Reconciliation）。

## **3. CP：选择 Consistency**

如果系统要求强一致性（Strong Consistency），情况就不同了。

假设 A、B、C 必须通过多数派（Quorum）确认才能完成写操作。

网络分区后：

- A、B 组成多数派，可以继续写入。
- C 是少数派，无法获得多数派确认。

因此：

- A、B 继续提供服务。
- C 拒绝或阻塞需要强一致性的请求。

这样就牺牲了部分 Availability，换取 Consistency。

## **4. 一个特别重要的细节**

CAP 中的 Availability 有严格的理论定义：

> Every request received by a non-failing node must result in a response.

也就是说：

只要节点本身没有故障，它收到的请求就必须返回一个有效响应，而不能无限等待或拒绝服务。

注意，返回错误并不算满足 CAP 的 Availability。

## **5. 联系 Bloomberg Entitlement**

假设 Bloomberg 有多个 entitlement server：

- Server A 在纽约。
- Server B 在伦敦。
- Server C 在东京。

发生网络分区后：

如果采用 AP 思路：

各节点继续使用本地权限缓存提供查询服务，即使缓存暂时不是最新的。

如果采用 CP 思路：

无法确认权限状态时，可能拒绝某些查询或授权操作。

这就涉及一个非常重要的安全问题：

**对于 Entitlement 系统，权限数据暂时不一致，究竟应该允许访问，还是拒绝访问？**

这不只是性能问题，也是安全策略问题。

特别注意：实际系统通常会对读取、授权和权限撤销采用不同策略，不能简单地给整个系统贴上 AP 或 CP 标签。
