# 5.1 C++多线程指针发布与生命周期管理

**介绍**: C++多线程指针发布与生命周期管理

在多线程场景（如权限系统、配置热更新等 Read-Mostly 架构）中，共享指针的并发读写是一个高频且容易出错的领域。

假设我们有如下数据结构：

```cpp
struct EntitlementSnapshot {
    int version;
    // 权限数据
};

std::atomic<EntitlementSnapshot*> current{nullptr};
```

如果把 `std::atomic<EntitlementSnapshot*>` 退化为普通的裸指针 `EntitlementSnapshot* current`，在多线程环境下会引发严重问题。本文将从底层内存模型到对象生命周期，逐层剖析其中的技术细节。

---

## 一、 场景设定

假设存在两个并发线程：
* **Writer 线程**：负责构建新的权限快照并更新全局指针。
* **Reader 线程**：负责读取当前全局指针并查询权限数据。

若使用普通裸指针：

```cpp
struct EntitlementSnapshot {
    int version;
};

EntitlementSnapshot* current = nullptr;

// Writer 线程
void update() {
    auto* snapshot = new EntitlementSnapshot{2};
    current = snapshot;
}

// Reader 线程
void query() {
    auto* snapshot = current;
    if (snapshot) {
        int version = snapshot->version;
    }
}
```

这种写法会导致两个核心问题：**Data Race（数据竞争）** 和 **Memory Visibility（内存可见性）**。

---

## 二、 核心问题剖析

### 1. Data Race（数据竞争）

当两个线程同时执行以下操作时：

| 时间线 | Writer 线程 | Reader 线程 |
| :--- | :--- | :--- |
| $T_1$ | `current = snapshot;` | `snapshot = current;` |

* **定义**：一个线程对普通非原子变量进行写操作，另一个线程同时对同一变量进行读操作，且两者之间没有建立同步关系。
* **后果**：在 C++ 内存模型中，Data Race 直接导致 **Undefined Behavior（未定义行为）**。
* **常见误区**：即便现代 64 位 CPU 在硬件层面能够保证对齐的指针读写不会发生物理上的“撕裂（Tearing）”，编译器优化（如寄存器缓存、指令重排）依然可能破坏程序逻辑。C++ 标准层面的 UB 不会因为硬件特性而豁免。

### 2. Memory Visibility（内存可见性）

再看一个更隐蔽的问题。将 Writer 拆解为分配、初始化、发布三个步骤：

```cpp
// Writer 线程
void update() {
    auto* snapshot = new EntitlementSnapshot; // 1. 分配内存
    snapshot->version = 2;                    // 2. 初始化数据
    current = snapshot;                       // 3. 发布指针
}

// Reader 线程
void query() {
    auto* snapshot = current;
    if (snapshot) {
        printf("%d\n", snapshot->version);    // 可能读到未初始化的脏数据！
    }
}
```

* **问题本质**：没有同步原语的约束，编译器和 CPU 可能会对指令进行重排（例如先执行 `current = snapshot`，再执行 `snapshot->version = 2`），或者其他 CPU 核心的 Cache 尚未同步。
* **结果**：Reader 线程虽然拿到了非空的 `current` 指针，但通过该指针读取到的 `version` 可能是未初始化的垃圾值。这需要通过建立 **Happens-Before（先行发生）** 关系来解决。

---

## 三、 使用 `std::atomic` 与内存序解决发布问题

通过 `std::atomic` 配合 `Release-Acquire` 内存序，可以同时解决数据竞争与内存可见性问题：

```cpp
std::atomic<EntitlementSnapshot*> current{nullptr};

// Writer 线程
void update() {
    auto* snapshot = new EntitlementSnapshot;
    snapshot->version = 2;

    // Release 语义：保证在此之前的写操作不会被重排到 store 之后
    current.store(snapshot, std::memory_order_release);
}

// Reader 线程
void query() {
    // Acquire 语义：保证在此之后的读操作不会被重排到 load 之前
    auto* snapshot = current.load(std::memory_order_acquire);

    if (snapshot) {
        printf("%d\n", snapshot->version); // 必然能安全读到 version == 2
    }
}
```

### 同步机制原理解析

| 角色 | 操作 | Memory Order | 核心作用 |
| :--- | :--- | :--- | :--- |
| **Writer** | `current.store()` | `memory_order_release` | 发布对象，并确保此前所有内存写入对其他线程可见 |
| **Reader** | `current.load()` | `memory_order_acquire` | 获取对象，并同步 Writer 在 release 之前的所有写入 |

当 Reader 的 `acquire load` 读取到 Writer 的 `release store` 所写入的值时，两者之间便建立了 **Synchronizes-With** 关系，进而构成了跨线程的 **Happens-Before** 约束：

```text
Writer Thread                        Reader Thread
-------------                        -------------
snapshot->version = 2;
       │
       ▼
current.store(snapshot, release) ──► current.load(acquire)
       (Synchronizes-With)                  │
                                            ▼
                                     读取 snapshot->version (安全！)
```

---

## 四、 进阶陷阱：Object Lifetime（对象生命周期）

**`std::atomic<T*>` 只解决了指针本身的并发安全与数据发布问题，并没有解决指针所指向对象的生命周期管理。**

如果 Writer 在更新指针后直接销毁旧对象，就会引发灾难：

```cpp
void update() {
    auto* old = current.load(std::memory_order_relaxed);
    auto* snapshot = new EntitlementSnapshot{2};
    current.store(snapshot, std::memory_order_release);
    
    delete old; // 危险！可能仍有 Reader 正在使用 old
}
```

### 竞态时序（Use-After-Free）

```text
Reader Thread                           Writer Thread
-------------                           -------------
snapshot = current.load(acquire)
                                        current.store(new_snapshot, release)
                                        delete old_snapshot  <-- 内存已释放！
int v = snapshot->version;  <-- 崩溃 / Use-After-Free
```

为了安全地回收旧对象，必须引入专门的内存回收机制：
1. **Hazard Pointer（险象指针）**：Reader 声明自己正在访问的指针，Writer 延迟释放被引用的对象。
2. **Epoch-Based Reclamation (EBR)**：基于全局时代（Epoch）推进，确认所有线程都已离开旧时代后再批量回收。
3. **RCU (Read-Copy-Update)**：读端无锁进入临界区，写端等待所有已存在的读端临界区结束后再释放旧数据。
4. **原子智能指针**：如 C++20 引入的 `std::atomic<std::shared_ptr<T>>`（注意：C++17 中需使用 `std::atomic_load` / `std::atomic_store` 等自由函数操作 `shared_ptr`，但性能通常不如无锁回收方案）。

---

## 五、 总结：并发内存管理的三个层次

在构建高并发 Read-Mostly 系统时，需要清晰区分以下三个不同维度的技术方案：

| 技术手段 | 解决的核心问题 |
| :--- | :--- |
| **`std::atomic<T*>`** | 指针变量本身的并发读写，消除 Data Race |
| **`memory_order_release / acquire`** | 对象内部成员初始化的跨线程可见性（Happens-Before） |
| **Hazard Pointer / EBR / RCU** | 旧对象的安全回收，防止 Use-After-Free |

### 完整架构数据流

```text
  [Writer 线程]
        │
        ├─ 1. 创建并初始化新的 Snapshot
        │
        ├─ 2. current.store(new_ptr, release)  ──► 解决并发写 & 内存可见性
        │
        └─ 3. 将 old_ptr 移交回收器 ──────────────► Hazard Pointer / EBR / RCU (解决生命周期)
                                                            ▲
  [Reader 线程]                                             │
        │                                                   │
        ├─ 1. current.load(acquire) ────────────────────────┤ (注册读取保护)
        │                                                   │
        ├─ 2. 安全读取 Snapshot 数据                        │
        │                                                   │
        └─ 3. 结束读取 ─────────────────────────────────────┘ (解除读取保护)
```

> **核心结论**：`std::atomic<EntitlementSnapshot*>` 只是线程安全快照管理机制的第一步，必须结合合理的内存回收策略（Reclamation），才能构成完整、健壮的无锁并发方案。
