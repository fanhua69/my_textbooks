# 1.2.1.13 本地权限快照

**介绍**: 本地权限快照

在这条链路里，**“本地权限快照 / Cache”**就是**直接驻留在在线服务当前进程内存（或本机极近存储）里的那份“权限副本”**。

它由前面的“异步同步线程 / Consumer”从“Durable Event Log”收到变更事件后不断更新，然后专门给“在线请求线程”做极速只读查询。

用大白话讲，就是：**把本来存在远端数据库里的权限数据，提前同步一份“随身小抄”放在在线业务进程的内存里，在线查权限时直接翻小抄，不用每次都跑去查远端数据库。**

---

## 1. 它到底“是啥”？

* **本地（Local）：** 跟着当前在线服务实例走（就在当前进程内存里，比如 `std::unordered_map`、并发哈希表、无锁/读写锁保护的内存结构，或本机嵌入式存储），**不走跨网络 RPC / SQL 查询**。
* **权限快照（Snapshot）：** 某一时刻权限状态的完整或增量视图（例如某个 `user_id` 当前拥有哪些 `role` / `permission` / `entitlement`）。
* **Cache（缓存）：** 为加速在线读请求而维护的副本；在权限校验场景下，它通常更偏向**全量或准全量内存态视图**，而不是只缓存少量热点 key 的普通缓存。


## 2. 它“干嘛的”？核心价值有 4 点

1. **压低在线鉴权延迟（微秒/亚毫秒级）：**
在线请求每次进网关或业务接口都要做权限检查。如果每次都查远端数据库或调用远端权限中心，网络往返（RTT）和数据库锁/索引开销会让延迟从几十微秒飙升到几毫秒甚至更高。查本地内存几乎没有网络开销。
2. **扛住高并发读流量（保护权威数据库）：**
权限通常是“写少读多”（改权限是低频后台操作，查权限是高频在线请求）。在线请求全打到本地快照上，权威数据库和权限管理服务就不会被海量鉴权请求压垮。
3. **提升可用性（弱依赖 / 局部容错）：**
即使权威数据库或事件通道出现短暂抖动、网络波动，只要本地权限快照还在，在线请求线程依然能用已有快照继续做权限校验（代价是期间可能存在短暂的数据延迟）。
4. **把“异步同步”和“在线查询”彻底拆开：**
* **异步同步线程 / Consumer** 负责慢活、重活：接收事件、解析变更、更新快照结构。
* **在线请求线程** 只负责快活：只读查快照，不被同步逻辑阻塞。


## 之所以叫“快照”（Snapshot）**，

是因为它在在线请求线程眼里，代表的是**“某一个特定时间点（或某个版本号/事件位点）的完整权限状态定格”——就像给正在变化的权限系统拍了一张照片。

用大白话和系统视角拆解，主要有 4 个原因：

---

### 1. 它反映的是“某个时间点 / 版本号”的状态定格

权限数据在后台是会不断变化的（比如新增用户、撤销角色、修改策略）。但对于在线请求线程来说，它读到的这份内存数据，对应的是**截至某个事件序列号（Offset / Version）为止的权限视图**。

* 就像拍照片时，镜头把“按下快门那一刻”的画面定格下来；
* 快照也是把“同步到第 $N$ 条事件时”的权限全貌定格在内存中，供在线线程随时查阅。

---

### 2. 它是一个“可整体读取或整份替换”的视图，而不是零散记录

如果只是零散地碰运气缓存几个 Key，通常更习惯叫 **Cache（缓存）**；而叫 **Snapshot（快照）**，往往强调**视图的完整性和一致性边界**：

* **全量或准全量状态：** 在线查权限时，往往需要知道“某主体当前拥有的完整权限集合 / 角色映射”，快照提供的是一个自洽的状态视图。
* **整份发布 / 原子切换：** 很多实现里，后台异步线程构建好新版本状态后，通过原子指针替换（如 `std::atomic<std::shared_ptr<const Snapshot>>` 或 RCU 思路）让在线线程瞬间切到新快照。在线线程看到的始终是一份完整的“照片”，不会读到改了一半、前后矛盾的撕裂状态。

---

### 3. 它和“事件日志（Event Log）”是天然一对：日志是录像，快照是照片

在事件驱动 / CQRS / 流式同步架构里，“日志”和“快照”经常成对出现：

* **Durable Event Log（事件日志）像“连续录像”：** 记录每一次“谁改了谁的什么权限”的历史动作（+ / - / 更新）。如果从头回放录像，也能还原出当前状态，但回放太慢。
* **本地权限快照像“当前帧画面 / 照片”：** 把录像回放到最新位置后定格出来的现成结果。在线查询不用从头算起，直接看当前这一“帧”就行。

---

### 4. 为什么经常写成“本地权限快照 / Cache”？

把两个词并列写在一起，是因为不同团队、不同实现方式侧重点略有不同：

* **偏重“状态视图与一致性边界”时**，大家叫 **Snapshot（快照）**（尤其是全量加载 + 增量事件推进 + 版本号/指针切换的内存态）。
* **偏重“为加速在线读而维护的副本”时**，大家叫 **Cache（缓存）**（尤其是带 TTL、淘汰策略或按需加载的读副本）。

在一条异步同步链路里，它既是**事件流回放出来的状态快照**，又是**服务于在线低延迟查询的读缓存**，所以工程上常把两者放在一起写。

---

### 3. 在整条链路中的位置与职责

* **上游（写侧 / 权威源）：** `权威数据库 / 权限管理服务` 决定“最新真相是什么”，通过 `事件发布机制` 写进 `Durable Event Log`。
* **中间搬运工：** `异步同步线程 / Consumer` 消费事件日志，把最新权限状态写进 `本地权限快照 / Cache`。
* **下游（读侧 / 在线路径）：** `在线请求线程` 收到用户请求后，直接读 `本地权限快照 / Cache` 完成放行或拦截。

---

### 4. 代价是什么？（工程上必须注意的权衡）

既然它这么快，为什么不直接取代权威数据库？因为它是**异步更新的副本**，天然带来两个问题：

* **最终一致性（有同步延迟）：** 管理员刚把某个用户的权限改掉，事件还没传到或 Consumer 还没刷完内存时，在线请求线程查到的可能还是旧权限（毫秒到秒级窗口）。
* **内存占用与并发安全：** 权限数据量大时，每个在线实例都存一份会占内存；同时存在“Consumer 写/换快照”和“在线线程读快照”，需要处理好并发安全（如读写锁、原子指针切换/RCU 思路、版本号防乱序）。

一句话总结：**“本地权限快照 / Cache”就是在线鉴权时的“内存级本地小抄”——用异步同步带来的短暂延迟，换取在线请求极低的查询延迟和极高的读吞吐。**
