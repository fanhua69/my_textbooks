# 1.2.1.17.02 事件丢失（Event Loss）

**介绍**: 事件丢失（Event Loss）

> **简介**：假设用户的权限被撤销：

---

## 问题是什么？

假设用户的权限被撤销：

``` text
T1: 数据库提交：撤销 User A 对 Security X 的访问权
T2: 系统产生 PermissionRevoked 事件
T3: 同步线程收到事件
T4: 本地缓存删除对应权限
```

如果 T2 到 T3
之间发生故障，事件没有可靠地送达消费者，那么本地缓存可能继续保留已经撤销的权限。

对于权限系统，这不只是数据不一致，而可能成为安全漏洞：用户已经失去权限，但某个服务节点仍然允许访问。

事件丢失常见原因：

-   数据库事务已经提交，但进程在发布事件前崩溃。
-   消息只放在进程内存队列中，进程崩溃后队列内容消失。
-   消息代理（Message Broker）故障，消息没有持久化。
-   消费者确认（ACK）时机不正确，导致消息被提前认为已处理。
-   网络断开期间，生产者或消费者没有可靠的补偿机制。

## Durable Message Queue（持久化消息队列）

Durable Message Queue
的核心思想是：消息不能只存在于生产者或消费者的内存中，而应先写入可恢复的持久化存储。

``` text
Producer
   |
   | publish
   v
Durable Message Queue
   |  持久化消息
   |
   v
Consumer
   |
   | process successfully
   v
ACK
```

通常的处理顺序是：

1.  生产者发布事件。
2.  消息代理将事件写入持久化日志或磁盘。
3.  消费者读取事件。
4.  消费者成功更新本地状态。
5.  消费者发送 ACK。
6.  消息代理才允许推进消费位置或删除相应消息（具体取决于系统实现）。

关键原则：**先完成业务处理，再确认消息已处理。**

如果消费者在处理完成前就
ACK，之后即使崩溃，消息也可能不会重发，从而造成数据丢失。

如果消费者处理完成、但在 ACK
前崩溃，消息可能被再次投递。这会造成重复处理，因此还需要幂等机制。

常见技术包括
Kafka、Pulsar、RabbitMQ（需正确配置持久化、确认和复制策略）等。仅仅使用某个消息队列产品，并不自动意味着端到端不丢消息；还必须检查生产者确认、消息持久化、复制、消费者
ACK 和故障恢复配置。

## CDC（Change Data Capture，变更数据捕获）

CDC
是另一种重要方案。它不是让业务代码在数据库事务提交后再"尽力发布"事件，而是从数据库的变更日志中捕获已经提交的变更。

例如：

``` text
业务事务
   |
   v
Database
   |
   +----> Transaction Log / WAL / Binlog
                       |
                       v
                  CDC Connector
                       |
                       v
                  Event Stream
                       |
                       v
                    Consumer
```

数据库事务和日志写入由数据库自身的事务机制协调。CDC
工具读取事务日志，把已提交的行变更转换成事件。

这样可以避免一个经典问题：

``` text
数据库提交成功
       |
       v
应用进程崩溃
       |
       v
事件还没发布
```

因为变更已经存在于数据库日志中，CDC 可以在恢复后继续读取。

常见 CDC 技术包括 Debezium、数据库原生逻辑复制，以及基于 MySQL
Binlog、PostgreSQL WAL 的订阅机制。

需要注意：

-   CDC
    通常捕获的是数据变更，不一定天然等于业务事件。需要设计事件语义和映射规则。
-   CDC Connector 自身也需要保存 offset / checkpoint，并具备恢复能力。
-   数据库日志可能被清理。如果消费者停机太久，所需日志已经不存在，就可能必须重新做全量快照。
-   需要考虑事务边界、表结构变更、主键、删除记录和 schema evolution。

## Transactional Outbox（事务性发件箱）

如果应用需要发布具有明确业务语义的事件，Transactional Outbox
是常见方案。

在同一个数据库事务中同时写业务数据和 outbox 表：

``` sql
BEGIN;

UPDATE entitlements
SET enabled = FALSE
WHERE user_id = 'A' AND security_id = 'X';

INSERT INTO outbox(event_id, event_type, payload)
VALUES ('evt-1001', 'PermissionRevoked', '{...}');

COMMIT;
```

因为业务更新和 outbox 插入处于同一事务：

-   两者一起提交；
-   或者两者一起回滚。

后台 Publisher 再读取 outbox
表并发布消息。发布成功后记录处理状态，或者由 CDC 读取 outbox 表。

Outbox 解决的是"数据库提交了，但应用没能可靠发布事件"的双写问题（Dual
Write Problem）。它不能自动解决消费者重复、乱序等所有问题。

## 小结

  ------------------------------------------------------------------------------------------
  方案                    主要解决什么                       关键代价或注意点
  ----------------------- ---------------------------------- -------------------------------
  Durable Message Queue   消息在代理和消费者故障后仍可恢复   需要正确配置持久化、复制、ACK

  CDC                     从数据库已提交的变更日志恢复发布   需要管理
                                                             offset、日志保留和事件语义

  Transactional Outbox    业务数据与待发布事件原子提交       需要 Publisher / CDC 和 outbox
                                                             清理策略
  ------------------------------------------------------------------------------------------
