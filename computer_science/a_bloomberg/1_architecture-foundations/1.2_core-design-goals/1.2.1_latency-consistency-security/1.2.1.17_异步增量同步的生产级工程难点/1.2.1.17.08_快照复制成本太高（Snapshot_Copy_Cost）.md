## 为什么复制快照会成为瓶颈？

一种常见的无锁读设计是：

-   读线程只读取不可变快照。
-   后台线程构造一份新快照。
-   新快照构建完成后，原子切换指针。
-   旧快照等读线程退出后再回收。

这种方式能让读线程避免互斥锁，但每次更新都复制整个数据集，成本可能很高。

假设：

-   权限快照有 1,000 万条记录。
-   每条记录平均占用 64 bytes（这里只用于估算）。
-   每次更新都完整复制快照。

仅数据主体就约为：

\[ 10\^7 `\times 64`{=tex} = 640,MB \]

如果每秒需要复制多次，内存带宽、分配器、缓存命中率和 GC /
回收成本都会成为问题。

## Sharding（分片）

Sharding 是把一个大状态拆成多个相对独立的小状态。

例如按 user_id 哈希：

``` text
Global Entitlement State
          |
          +---- Shard 0
          +---- Shard 1
          +---- Shard 2
          +---- ...
          +---- Shard N
```

更新某个用户时，只需要重建或替换对应分片，而不是复制整个全局快照。

如果有 256 个大小接近的分片，一次更新平均只需处理总数据的约
1/256（理想化估算）。

但分片并非没有代价：

-   查询需要确定目标分片。
-   跨用户、跨资源查询可能要访问多个分片。
-   分片大小可能不均匀，出现热点。
-   全局一致性快照和全量切换更复杂。
-   如果一个请求需要同时读取多个分片，必须定义它能否看到不同时间点的版本。

选择分片键时，应优先考虑最常见的查询和更新粒度。

## Persistent Data Structure（持久化数据结构）

这里的 Persistent
不是"写入磁盘的持久化"，而是指**保留历史版本的不可变数据结构**（Persistent
/ Immutable Data Structure）。

更新时不复制全部数据，而是只复制从根节点到被修改节点的路径，其他未变化节点由新旧版本共享。

例如持久化树：

``` text
旧版本 Root A                 新版本 Root B
      |                            |
      v                            v
    Node 1                       Node 1'
      |                            |
      +---- Node 2                 +---- Node 2'
      |                                  |
      +---- Node 3 ----------------------+---- Node 3
             共享未修改节点
```

对平衡树而言，单次更新通常只需要创建 (O(`\log `{=tex}N))
个新节点，而不是复制 (O(N)) 个元素。

常见结构：

-   Persistent Trie
-   Persistent Hash Trie
-   Persistent Balanced Tree
-   Copy-on-Write Tree

优点：

-   新旧版本可以共享大部分内存。
-   读线程可以继续使用旧版本。
-   更新可以生成新根指针，再原子发布。
-   历史版本可用于回滚或一致性读取。

代价：

-   节点分配和指针追踪可能影响缓存局部性。
-   内存管理更复杂。
-   高频更新可能产生大量短命节点。
-   并发回收仍需要 epoch、引用计数或其他安全机制。

## RCU（Read-Copy-Update）

RCU 是一种面向读多写少场景的并发同步技术，常见于 Linux
内核，也可用于用户态设计。

其基本思想：

1.  读线程进入读侧临界区。
2.  读线程读取当前指针并访问对象。
3.  写线程复制或构造新版本。
4.  写线程原子发布新指针。
5.  写线程等待一个 Grace
    Period，确保所有可能仍在访问旧版本的读线程都已退出。
6.  确认安全后回收旧版本。

``` text
Reader 1:  ---- read old version -------- exit
Reader 2:       ---- read old version -------- exit

Writer:   build new -> publish new -> wait grace period -> reclaim old
```

读侧通常非常轻量，甚至可以做到不使用传统互斥锁；但具体成本取决于 RCU
实现和读侧临界区设计。

RCU 的关键不是"写线程立刻删除旧对象"，而是：

**发布新版本与安全回收旧版本是两个不同的步骤。**

如果写线程原子替换指针后马上释放旧对象，仍在读取旧对象的线程就可能访问已释放内存，造成
Use-After-Free。

RCU 常见实现方式或相关技术包括：

-   Linux kernel RCU。
-   用户态 RCU（Userspace RCU / liburcu）。
-   Epoch-Based Reclamation（EBR）。
-   QSBR（Quiescent State Based Reclamation）。
-   Hazard Pointers（原理不同，但同样用于安全回收并发访问的对象）。

这些机制并不完全等价。RCU 通常通过宽限期判断旧版本何时可回收；Hazard
Pointers 则让读线程显式声明自己正在保护哪些对象。

## 三种方案如何选择？

  ----------------------------------------------------------------------------------------------------------
  方案           核心思路                     更新成本               读路径           主要复杂度
  -------------- ---------------------------- ---------------------- ---------------- ----------------------
  Sharding       把全局状态拆成多个独立分片   更新局部数据           根据 key         跨分片一致性、热点
                                                                     定位分片         

  Persistent     结构共享，只复制修改路径     通常与树高相关         不可变结构读取   节点分配、缓存局部性
  Data Structure                                                                      

  RCU            发布新版本，延迟回收旧版本   取决于新版本构造方式   极轻量读侧       Grace Period、内存回收
  ----------------------------------------------------------------------------------------------------------

这三者不是互斥选项，可以组合使用。例如：

-   先按用户 ID 分片；
-   每个分片内部使用不可变哈希树；
-   通过 RCU 或 epoch 机制发布和回收分片版本。
