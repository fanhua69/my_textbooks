# 1.2.1.17.07 快照过旧（Stale Snapshot）

**介绍**: 快照过旧（Stale Snapshot）

> **简介**：即使同步线程没有崩溃，也不代表本地缓存一定足够新。

---

## 问题是什么？

即使同步线程没有崩溃，也不代表本地缓存一定足够新。

可能出现：

-   消费者处理速度低于事件产生速度。
-   某个分区持续积压（Consumer Lag）。
-   同步线程仍存活，但卡在某条消息或外部依赖上。
-   心跳正常，但实际数据版本长期没有前进。

因此，"进程活着"不等于"数据新鲜"。

## Version Monitoring（版本监控）

系统应监控本地状态与权威数据之间的进度差异。

常见指标：

  指标                        含义
  --------------------------- ------------------------------------------
  Last Applied Version        本地最后应用的版本
  Last Applied Offset         本地最后应用的日志位置
  Consumer Lag                已产生但尚未消费的事件数量或 offset 差距
  Last Successful Sync Time   最近一次成功同步时间
  Snapshot Age                当前快照距离生成时刻的时间
  Partition Lag               每个分区各自的消费延迟

只看时间戳并不总是可靠：系统时钟可能偏差，事件也可能没有均匀产生。最好同时监控日志位置、版本号和时间。

还应设置阈值：

``` text
Healthy:  lag <= 1,000 events
Degraded: lag > 1,000 events
Stale:    no progress for 30 seconds
```

这里的数值只是示例，实际阈值应根据权限变更频率、业务风险和可接受的撤权延迟确定。

## Fail-Closed（失败时拒绝）

权限系统必须考虑安全优先级。

-   Fail-Open：无法确认权限时，仍允许访问。
-   Fail-Closed：无法确认权限时，拒绝访问。

如果本地缓存过旧，继续允许访问可能让已经撤销的权限继续生效。因此，对高风险操作，常采用
Fail-Closed。

但 Fail-Closed
不一定意味着所有服务立即全面拒绝所有请求。可以根据风险分级：

  场景               可能策略
  ------------------ ----------------------------------------
  高敏感数据访问     缓存超过严格阈值时拒绝
  普通低风险读取     在明确的短暂宽限期内使用本地缓存
  权限变更管理操作   无法确认权威状态时拒绝提交
  监控与健康检查     继续提供状态信息，但标记权限缓存不可用

关键是策略必须明确、可观测、可审计，不能让"暂时用旧缓存"成为隐式默认行为。

## 撤权延迟（Revocation Latency）

权限系统需要定义从权威撤权到所有服务节点停止授权之间允许的最大时间：

\[ RevocationLatency = T\_{all nodes updated} - T\_{authority commit} \]

例如业务要求撤权在 2 秒内传播到所有节点，那么系统必须监控并验证这一
SLO（Service Level Objective）。

对于无法达到该 SLO
的节点，应进入降级或拒绝服务状态，而不是继续假设缓存是最新的。
