# 1.2.1.09 在线权限系统：异步增量同步的生产级工程难点

**介绍**: 在线权限系统：异步增量同步的生产级工程难点

## 1. 背景：为什么"订阅事件并更新缓存"远远不够？

* 在线权限系统（Entitlement System）通常把权限数据从权威数据源（Authoritative Source）同步到各个服务节点的本地缓存（Local Cache），让请求线程只进行内存查询。

* 典型路径如下：

``` text
权威数据库 / 权限管理服务
          |
          | 事务提交
          v
    事件发布机制
          |
          v
   Durable Event Log
          |
          v
  异步同步线程 / Consumer
          |
          v
   本地权限快照 / Cache
          |
          v
   在线请求线程查询
```

* 这种设计把慢速 I/O 和同步工作移出在线查询热路径（Hot Path），但也引入了分布式系统中的可靠性问题：消息可能丢失、重复、乱序；消费者可能崩溃；网络可能中断；本地快照可能落后于权威状态。

下面逐项分析这些问题，以及常见解决方案的原理、适用条件和代价。

------------------------------------------------------------------------

## 2. 事件丢失（Event Loss）

### 2.1 问题是什么？

假设用户的权限被撤销：

``` text
T1: 数据库提交：撤销 User A 对 Security X 的访问权
T2: 系统产生 PermissionRevoked 事件
T3: 同步线程收到事件
T4: 本地缓存删除对应权限
```

如果 T2 到 T3
之间发生故障，事件没有可靠地送达消费者，那么本地缓存可能继续保留已经撤销的权限。

对于权限系统，这不只是数据不一致，而可能成为安全漏洞：用户已经失去权限，但某个服务节点仍然允许访问。

事件丢失常见原因：

-   数据库事务已经提交，但进程在发布事件前崩溃。
-   消息只放在进程内存队列中，进程崩溃后队列内容消失。
-   消息代理（Message Broker）故障，消息没有持久化。
-   消费者确认（ACK）时机不正确，导致消息被提前认为已处理。
-   网络断开期间，生产者或消费者没有可靠的补偿机制。

### 2.2 Durable Message Queue（持久化消息队列）

Durable Message Queue
的核心思想是：消息不能只存在于生产者或消费者的内存中，而应先写入可恢复的持久化存储。

``` text
Producer
   |
   | publish
   v
Durable Message Queue
   |  持久化消息
   |
   v
Consumer
   |
   | process successfully
   v
ACK
```

通常的处理顺序是：

1.  生产者发布事件。
2.  消息代理将事件写入持久化日志或磁盘。
3.  消费者读取事件。
4.  消费者成功更新本地状态。
5.  消费者发送 ACK。
6.  消息代理才允许推进消费位置或删除相应消息（具体取决于系统实现）。

关键原则：**先完成业务处理，再确认消息已处理。**

如果消费者在处理完成前就
ACK，之后即使崩溃，消息也可能不会重发，从而造成数据丢失。

如果消费者处理完成、但在 ACK
前崩溃，消息可能被再次投递。这会造成重复处理，因此还需要幂等机制。

常见技术包括
Kafka、Pulsar、RabbitMQ（需正确配置持久化、确认和复制策略）等。仅仅使用某个消息队列产品，并不自动意味着端到端不丢消息；还必须检查生产者确认、消息持久化、复制、消费者
ACK 和故障恢复配置。

### 2.3 CDC（Change Data Capture，变更数据捕获）

CDC
是另一种重要方案。它不是让业务代码在数据库事务提交后再"尽力发布"事件，而是从数据库的变更日志中捕获已经提交的变更。

例如：

``` text
业务事务
   |
   v
Database
   |
   +----> Transaction Log / WAL / Binlog
                       |
                       v
                  CDC Connector
                       |
                       v
                  Event Stream
                       |
                       v
                    Consumer
```

数据库事务和日志写入由数据库自身的事务机制协调。CDC
工具读取事务日志，把已提交的行变更转换成事件。

这样可以避免一个经典问题：

``` text
数据库提交成功
       |
       v
应用进程崩溃
       |
       v
事件还没发布
```

因为变更已经存在于数据库日志中，CDC 可以在恢复后继续读取。

常见 CDC 技术包括 Debezium、数据库原生逻辑复制，以及基于 MySQL
Binlog、PostgreSQL WAL 的订阅机制。

需要注意：

-   CDC
    通常捕获的是数据变更，不一定天然等于业务事件。需要设计事件语义和映射规则。
-   CDC Connector 自身也需要保存 offset / checkpoint，并具备恢复能力。
-   数据库日志可能被清理。如果消费者停机太久，所需日志已经不存在，就可能必须重新做全量快照。
-   需要考虑事务边界、表结构变更、主键、删除记录和 schema evolution。

### 2.4 Transactional Outbox（事务性发件箱）

如果应用需要发布具有明确业务语义的事件，Transactional Outbox
是常见方案。

在同一个数据库事务中同时写业务数据和 outbox 表：

``` sql
BEGIN;

UPDATE entitlements
SET enabled = FALSE
WHERE user_id = 'A' AND security_id = 'X';

INSERT INTO outbox(event_id, event_type, payload)
VALUES ('evt-1001', 'PermissionRevoked', '{...}');

COMMIT;
```

因为业务更新和 outbox 插入处于同一事务：

-   两者一起提交；
-   或者两者一起回滚。

后台 Publisher 再读取 outbox
表并发布消息。发布成功后记录处理状态，或者由 CDC 读取 outbox 表。

Outbox 解决的是"数据库提交了，但应用没能可靠发布事件"的双写问题（Dual
Write Problem）。它不能自动解决消费者重复、乱序等所有问题。

### 2.5 小结

  ------------------------------------------------------------------------------------------
  方案                    主要解决什么                       关键代价或注意点
  ----------------------- ---------------------------------- -------------------------------
  Durable Message Queue   消息在代理和消费者故障后仍可恢复   需要正确配置持久化、复制、ACK

  CDC                     从数据库已提交的变更日志恢复发布   需要管理
                                                             offset、日志保留和事件语义

  Transactional Outbox    业务数据与待发布事件原子提交       需要 Publisher / CDC 和 outbox
                                                             清理策略
  ------------------------------------------------------------------------------------------

## 3. 事件重复（Duplicate Events）

### 3.1 为什么会重复？

在分布式系统中，消费者可能已经完成处理，但 ACK 没有成功送达消息代理：

``` text
Consumer 收到 Event E
       |
       v
更新本地缓存成功
       |
       v
发送 ACK
       |
       X 网络断开，ACK 丢失
       |
       v
消息代理重新投递 Event E
```

消费者无法仅凭 ACK
丢失判断上一次处理是否成功，因此常见消息系统采用至少一次投递（At-least-once
Delivery）。

At-least-once
的含义是：消息可能被投递多次，但系统努力保证消息不会因为一次短暂故障就永久消失。

因此，消费者必须考虑重复事件。

### 3.2 Idempotency（幂等性）

幂等（Idempotent）指：同一个操作执行一次或多次，最终效果相同。

数学上：

\[ f(f(x)) = f(x) \]

例如：

``` cpp
// 幂等：把权限状态设置为 revoked
void apply(const PermissionRevoked& event) {
    cache.set(event.user_id, event.security_id, Revoked);
}
```

无论执行一次还是三次，最终状态都是 Revoked。

相反，下面这种操作不是天然幂等的：

``` cpp
// 非幂等：每处理一次就递减
void apply(const PermissionRevoked& event) {
    --active_permission_count;
}
```

如果事件重复投递，计数器就会被多减。

更好的方式是使用事件携带的目标状态，或者在更新计数器时依据唯一事件 ID
做去重。

### 3.3 Event ID 去重

每个事件都应有稳定且唯一的 ID：

``` text
event_id = evt-1001
```

消费者可以维护已处理事件集合：

``` sql
BEGIN;

INSERT INTO processed_events(event_id)
VALUES ('evt-1001');

-- 只有 event_id 首次插入成功时，才执行对应业务更新。

COMMIT;
```

在数据库消费者中，去重记录和业务更新应放在同一个事务里，否则可能出现"记录已去重，但业务更新没完成"或相反的故障窗口。

对于纯内存缓存消费者，可以采用：

-   有界去重窗口（Deduplication Window）。
-   每个分区的最后处理 offset。
-   每个实体的最新版本号。
-   可恢复的消费 checkpoint。

不要无限保存所有 event ID，否则去重集合本身会无限增长。

### 3.4 权限同步中更实用的策略：状态设置优于状态累加

如果事件表达的是状态：

``` text
PermissionGranted(user=A, resource=X, version=10)
PermissionRevoked(user=A, resource=X, version=11)
```

消费者应尽量把事件解释为"将实体设置为某个版本的状态"，而不是"执行一次增量动作"。

这会让重复处理更容易变成幂等操作。

但仅靠幂等还不够：如果旧事件在新事件之后到达，仍可能把状态覆盖回旧值。这就引出事件乱序问题。

## 4. 事件乱序（Out-of-Order Events）

### 4.1 问题是什么？

假设同一个用户、同一项资源的权限发生两次变化：

``` text
Version 10: PermissionGranted
Version 11: PermissionRevoked
```

正确顺序应为：

``` text
Granted -> Revoked
```

但由于多个生产者、网络延迟、重试或多个消费者并行处理，消费者可能看到：

``` text
Revoked (v11)
Granted (v10)
```

如果消费者简单地"收到什么就应用什么"，最后就会错误地恢复权限。

### 4.2 Sequence Number（序列号）

生产者为事件分配递增序列号：

``` text
Entity: (User A, Resource X)

Event 1: Granted, version = 10
Event 2: Revoked, version = 11
Event 3: Granted, version = 12
```

消费者维护当前版本：

``` cpp
void apply(const Event& event) {
    auto& current = cache[event.key];

    if (event.version <= current.version) {
        return; // 重复或过期事件
    }

    current.state = event.state;
    current.version = event.version;
}
```

这样即使 v10 在 v11 后到达，也会因为版本较旧而被忽略。

### 4.3 Version（版本号）与 Sequence Number 的区别

两者经常被混用，但侧重点不同：

-   Sequence Number 通常强调事件在某个有序流中的先后位置。
-   Version 通常强调某个实体或对象当前状态的版本。

例如：

-   全局日志 offset：标识整个分区日志中的位置。
-   每分区 sequence number：标识该分区中的事件顺序。
-   每个用户权限记录的 version：标识该用户权限对象的状态版本。

必须明确版本号的作用域（Scope）。两个不同分区中的 offset
通常不能直接比较；两个不同实体的 version 也不能随意比较。

### 4.4 分区与顺序保证

如果同一实体的事件必须有序，通常让相同实体键（Entity
Key）进入同一个消息分区：

``` text
partition = hash(user_id, resource_id) % N
```

同一分区内由单一有序日志提供顺序保证，再由消费者按顺序处理。

不过：

-   分区只能保证分区内部的顺序，不保证不同分区之间的全局顺序。
-   多线程消费者如果把同一分区事件并行执行，仍可能破坏应用顺序。
-   重试队列、死信队列和重新投递也可能改变处理顺序。

### 4.5 检测版本缺口（Version Gap）

如果当前版本为 10，却收到版本 12，可能意味着版本 11 丢失或尚未到达。

有两种常见语义：

1.  **状态快照事件（State-based Event）**：v12
    携带完整的新状态。如果版本号可信，通常可以直接应用
    v12，并记录观察到缺口。
2.  **增量操作事件（Delta Event）**：v12 依赖 v11
    的结果。此时不能简单跳过
    v11，应暂存事件、等待缺失事件，或重新同步该实体。

必须先定义事件是"状态描述"还是"状态变更操作"，再决定如何处理缺口。

## 5. 后台线程崩溃（Background Worker Crash）

### 5.1 问题是什么？

异步同步线程可能在任意时刻崩溃：

-   读到事件后、更新缓存前崩溃。
-   更新缓存后、保存 checkpoint 前崩溃。
-   保存 checkpoint 后、更新缓存前崩溃（如果实现顺序错误）。
-   处理一批事件时只完成其中一部分。

重启后，系统必须知道从哪里继续，并避免漏掉未完成的更新。

### 5.2 Checkpoint（检查点）

Checkpoint 记录消费者已经可靠处理到哪里。

例如 Kafka 风格的日志：

``` text
Partition 0:
offset 100  processed
offset 101  processed
offset 102  processed
offset 103  not processed
```

消费者的 checkpoint
应指向"下次应读取的位置"，或者记录"最后一个已完成的位置"；具体定义必须统一，避免
off-by-one 错误。

最重要的规则是：

**不能把 checkpoint 推进到尚未可靠应用的事件之后。**

对于单线程顺序消费，一个安全的概念顺序是：

``` text
读取事件
   |
   v
应用到可恢复状态
   |
   v
持久化状态 / 确保状态可恢复
   |
   v
提交 checkpoint
```

但如果缓存只是进程内存，重启后会全部消失，那么仅保存消息 offset
并不能恢复缓存。此时必须：

-   从持久化快照恢复缓存，再从对应 offset 重放；或
-   重启后重新加载全量快照，再从快照对应的日志位置开始消费。

### 5.3 Replay（重放）

Replay 指从持久化事件日志中重新读取事件，重建目标状态。

例如：

``` text
Snapshot at offset 1000
        |
        v
Load snapshot
        |
        v
Replay events 1001, 1002, 1003, ...
        |
        v
Current local state
```

快照（Snapshot）提供一个较早的完整状态，事件日志（Event
Log）提供快照之后的变化。

如果没有快照，只从系统创建以来的第一条事件重放，恢复时间可能越来越长。

### 5.4 Snapshot 与 Checkpoint 必须配对

快照必须记录它对应的日志位置：

``` text
snapshot_version = 42
snapshot_offset  = 1000
```

恢复时：

1.  加载快照。
2.  确认快照对应 offset。
3.  从 offset 之后继续 Replay。
4.  达到当前日志末尾后，进入正常消费。

如果快照内容与 offset 不匹配，就可能漏应用或重复应用事件。

### 5.5 多分区场景

如果有多个分区，checkpoint 通常是一个向量：

``` text
partition 0 -> offset 1200
partition 1 -> offset 980
partition 2 -> offset 1500
```

不能随意把多个分区的 offset 合并成一个全局数字。

## 6. 同步通道断开（Synchronization Channel Disconnection）

### 6.1 问题是什么？

本地缓存依赖消息流持续更新。如果网络中断、消息代理不可用或 CDC Connector
停止，本地缓存就会逐渐落后。

``` text
Authority / Event Stream
          |
          X  network disconnected
          |
          v
Local Cache
```

在断开期间，用户可能已经被撤销权限，但本地节点仍保留旧授权。

因此，系统不仅要能恢复连接，还要能判断本地缓存是否仍然可信。

### 6.2 Full Resynchronization（全量重新同步）

如果断线期间的事件仍保留在可靠日志中，并且消费者 offset
仍在日志保留范围内，那么通常可以从最后一个 checkpoint
继续增量追赶（Catch-up）。

如果事件已经过期、offset
无效、数据版本不兼容，或者本地状态无法确认，就需要全量重新同步：

``` text
Detect stream failure
       |
       v
Mark local cache as stale
       |
       v
Obtain authoritative snapshot
       |
       v
Build new local cache
       |
       v
Start / resume event stream from snapshot position
       |
       v
Catch up to current position
       |
       v
Publish new cache as active
```

### 6.3 快照与事件流之间的边界是关键

全量同步最容易犯的错误，是快照和增量事件之间出现时间窗口。

错误示例：

``` text
T1: 获取数据库快照
T2: 权限发生变化，产生事件 E
T3: 开始订阅事件
```

如果 E 没有包含在快照里，又发生在订阅开始之前，那么 E 就会永久漏掉。

正确方案必须让快照与日志位置建立一致性关系。例如：

-   数据库支持一致性快照和 WAL / Binlog 位点关联。
-   CDC 提供 snapshot + streaming 的一致性切换机制。
-   使用日志屏障（Barrier）或明确的高水位（High Watermark）。

概念上：

``` text
Snapshot represents state through offset N
Replay starts at offset N + 1
```

这条边界必须由底层机制保证，而不是靠两个独立操作"差不多同时"完成。

### 6.4 原子切换（Atomic Swap）

不要在全量重建过程中逐条覆盖正在服务请求的缓存，否则请求可能看到半新半旧的数据。

更稳妥的方式是：

1.  在后台构建新的缓存实例。
2.  对新缓存应用增量事件，追到指定高水位。
3.  确认新缓存完整且健康。
4.  用原子指针切换（Atomic Pointer Swap）发布新缓存。
5.  延迟回收旧缓存，确保正在使用它的读线程已经退出。

## 7. 快照过旧（Stale Snapshot）

### 7.1 问题是什么？

即使同步线程没有崩溃，也不代表本地缓存一定足够新。

可能出现：

-   消费者处理速度低于事件产生速度。
-   某个分区持续积压（Consumer Lag）。
-   同步线程仍存活，但卡在某条消息或外部依赖上。
-   心跳正常，但实际数据版本长期没有前进。

因此，"进程活着"不等于"数据新鲜"。

### 7.2 Version Monitoring（版本监控）

系统应监控本地状态与权威数据之间的进度差异。

常见指标：

  指标                        含义
  --------------------------- ------------------------------------------
  Last Applied Version        本地最后应用的版本
  Last Applied Offset         本地最后应用的日志位置
  Consumer Lag                已产生但尚未消费的事件数量或 offset 差距
  Last Successful Sync Time   最近一次成功同步时间
  Snapshot Age                当前快照距离生成时刻的时间
  Partition Lag               每个分区各自的消费延迟

只看时间戳并不总是可靠：系统时钟可能偏差，事件也可能没有均匀产生。最好同时监控日志位置、版本号和时间。

还应设置阈值：

``` text
Healthy:  lag <= 1,000 events
Degraded: lag > 1,000 events
Stale:    no progress for 30 seconds
```

这里的数值只是示例，实际阈值应根据权限变更频率、业务风险和可接受的撤权延迟确定。

### 7.3 Fail-Closed（失败时拒绝）

权限系统必须考虑安全优先级。

-   Fail-Open：无法确认权限时，仍允许访问。
-   Fail-Closed：无法确认权限时，拒绝访问。

如果本地缓存过旧，继续允许访问可能让已经撤销的权限继续生效。因此，对高风险操作，常采用
Fail-Closed。

但 Fail-Closed
不一定意味着所有服务立即全面拒绝所有请求。可以根据风险分级：

  场景               可能策略
  ------------------ ----------------------------------------
  高敏感数据访问     缓存超过严格阈值时拒绝
  普通低风险读取     在明确的短暂宽限期内使用本地缓存
  权限变更管理操作   无法确认权威状态时拒绝提交
  监控与健康检查     继续提供状态信息，但标记权限缓存不可用

关键是策略必须明确、可观测、可审计，不能让"暂时用旧缓存"成为隐式默认行为。

### 7.4 撤权延迟（Revocation Latency）

权限系统需要定义从权威撤权到所有服务节点停止授权之间允许的最大时间：

\[ RevocationLatency = T\_{all nodes updated} - T\_{authority commit} \]

例如业务要求撤权在 2 秒内传播到所有节点，那么系统必须监控并验证这一
SLO（Service Level Objective）。

对于无法达到该 SLO
的节点，应进入降级或拒绝服务状态，而不是继续假设缓存是最新的。

## 8. 快照复制成本太高（Snapshot Copy Cost）

### 8.1 为什么复制快照会成为瓶颈？

一种常见的无锁读设计是：

-   读线程只读取不可变快照。
-   后台线程构造一份新快照。
-   新快照构建完成后，原子切换指针。
-   旧快照等读线程退出后再回收。

这种方式能让读线程避免互斥锁，但每次更新都复制整个数据集，成本可能很高。

假设：

-   权限快照有 1,000 万条记录。
-   每条记录平均占用 64 bytes（这里只用于估算）。
-   每次更新都完整复制快照。

仅数据主体就约为：

\[ 10\^7 `\times 64`{=tex} = 640,MB \]

如果每秒需要复制多次，内存带宽、分配器、缓存命中率和 GC /
回收成本都会成为问题。

### 8.2 Sharding（分片）

Sharding 是把一个大状态拆成多个相对独立的小状态。

例如按 user_id 哈希：

``` text
Global Entitlement State
          |
          +---- Shard 0
          +---- Shard 1
          +---- Shard 2
          +---- ...
          +---- Shard N
```

更新某个用户时，只需要重建或替换对应分片，而不是复制整个全局快照。

如果有 256 个大小接近的分片，一次更新平均只需处理总数据的约
1/256（理想化估算）。

但分片并非没有代价：

-   查询需要确定目标分片。
-   跨用户、跨资源查询可能要访问多个分片。
-   分片大小可能不均匀，出现热点。
-   全局一致性快照和全量切换更复杂。
-   如果一个请求需要同时读取多个分片，必须定义它能否看到不同时间点的版本。

选择分片键时，应优先考虑最常见的查询和更新粒度。

### 8.3 Persistent Data Structure（持久化数据结构）

这里的 Persistent
不是"写入磁盘的持久化"，而是指**保留历史版本的不可变数据结构**（Persistent
/ Immutable Data Structure）。

更新时不复制全部数据，而是只复制从根节点到被修改节点的路径，其他未变化节点由新旧版本共享。

例如持久化树：

``` text
旧版本 Root A                 新版本 Root B
      |                            |
      v                            v
    Node 1                       Node 1'
      |                            |
      +---- Node 2                 +---- Node 2'
      |                                  |
      +---- Node 3 ----------------------+---- Node 3
             共享未修改节点
```

对平衡树而言，单次更新通常只需要创建 (O(`\log `{=tex}N))
个新节点，而不是复制 (O(N)) 个元素。

常见结构：

-   Persistent Trie
-   Persistent Hash Trie
-   Persistent Balanced Tree
-   Copy-on-Write Tree

优点：

-   新旧版本可以共享大部分内存。
-   读线程可以继续使用旧版本。
-   更新可以生成新根指针，再原子发布。
-   历史版本可用于回滚或一致性读取。

代价：

-   节点分配和指针追踪可能影响缓存局部性。
-   内存管理更复杂。
-   高频更新可能产生大量短命节点。
-   并发回收仍需要 epoch、引用计数或其他安全机制。

### 8.4 RCU（Read-Copy-Update）

RCU 是一种面向读多写少场景的并发同步技术，常见于 Linux
内核，也可用于用户态设计。

其基本思想：

1.  读线程进入读侧临界区。
2.  读线程读取当前指针并访问对象。
3.  写线程复制或构造新版本。
4.  写线程原子发布新指针。
5.  写线程等待一个 Grace
    Period，确保所有可能仍在访问旧版本的读线程都已退出。
6.  确认安全后回收旧版本。

``` text
Reader 1:  ---- read old version -------- exit
Reader 2:       ---- read old version -------- exit

Writer:   build new -> publish new -> wait grace period -> reclaim old
```

读侧通常非常轻量，甚至可以做到不使用传统互斥锁；但具体成本取决于 RCU
实现和读侧临界区设计。

RCU 的关键不是"写线程立刻删除旧对象"，而是：

**发布新版本与安全回收旧版本是两个不同的步骤。**

如果写线程原子替换指针后马上释放旧对象，仍在读取旧对象的线程就可能访问已释放内存，造成
Use-After-Free。

RCU 常见实现方式或相关技术包括：

-   Linux kernel RCU。
-   用户态 RCU（Userspace RCU / liburcu）。
-   Epoch-Based Reclamation（EBR）。
-   QSBR（Quiescent State Based Reclamation）。
-   Hazard Pointers（原理不同，但同样用于安全回收并发访问的对象）。

这些机制并不完全等价。RCU 通常通过宽限期判断旧版本何时可回收；Hazard
Pointers 则让读线程显式声明自己正在保护哪些对象。

### 8.5 三种方案如何选择？

  ----------------------------------------------------------------------------------------------------------
  方案           核心思路                     更新成本               读路径           主要复杂度
  -------------- ---------------------------- ---------------------- ---------------- ----------------------
  Sharding       把全局状态拆成多个独立分片   更新局部数据           根据 key         跨分片一致性、热点
                                                                     定位分片         

  Persistent     结构共享，只复制修改路径     通常与树高相关         不可变结构读取   节点分配、缓存局部性
  Data Structure                                                                      

  RCU            发布新版本，延迟回收旧版本   取决于新版本构造方式   极轻量读侧       Grace Period、内存回收
  ----------------------------------------------------------------------------------------------------------

这三者不是互斥选项，可以组合使用。例如：

-   先按用户 ID 分片；
-   每个分片内部使用不可变哈希树；
-   通过 RCU 或 epoch 机制发布和回收分片版本。

## 10. 生产系统设计时必须明确的几个问题

在实现之前，建议把以下问题写成可验证的设计约束：

1.  **事件投递语义是什么？**
    At-most-once、At-least-once，还是通过额外机制实现业务上的
    effectively-once？
2.  **事件是否有唯一 ID？** 重复事件如何识别？
3.  **版本号的作用域是什么？** 全局、分区级，还是实体级？
4.  **事件表达完整状态还是增量操作？** 这决定能否跳过版本缺口。
5.  **checkpoint 在什么时机提交？** 如何避免先提交 offset、后应用状态？
6.  **快照对应哪个日志位置？** 如何保证 snapshot 与 event stream
    之间没有缺口？
7.  **消费者落后多少算 stale？** 触发什么降级策略？
8.  **撤权的最大传播延迟是多少？** 如何监控每个节点是否满足 SLO？
9.  **全量同步如何切换？** 如何避免请求线程看到半成品状态？
10. **旧快照何时可以释放？** 如何保证没有读线程仍在使用它？

### 最重要的工程原则

-   不要把"消息队列持久化"误认为整个同步链路绝对不会丢数据。
-   不要假设消息只会投递一次；设计幂等消费者。
-   不要假设事件天然有序；明确顺序保证和版本作用域。
-   不要把进程存活等同于缓存新鲜；监控实际同步进度。
-   不要在全量同步时直接修改正在服务请求的缓存；构建完成后再原子切换。
-   不要发布新快照后立即释放旧快照；必须使用安全的内存回收机制。
-   对权限撤销，必须明确新鲜度 SLO 和缓存过期时的 Fail-Closed 策略。

**总结：** 异步增量同步的难点并不是"如何收到事件并更新
map"，而是如何在消息丢失、重复、乱序、进程崩溃和网络分区等故障下，持续证明本地权限状态是完整、可恢复且足够新鲜的。对于权限系统，数据正确性和撤权安全性必须优先于单纯的可用性与吞吐量。
