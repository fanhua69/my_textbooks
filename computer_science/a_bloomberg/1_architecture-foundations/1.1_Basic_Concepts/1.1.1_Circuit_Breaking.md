# 熔断（Circuit Breaking）深度解析

**熔断（Circuit Breaking）**借鉴了电路保险丝的原理：当调用链路中的下游服务出现严重延迟或高比例报错时，上游调用方不再盲目等待或持续请求，而是直接“跳闸”（快速失败），释放线程、连接和计算资源，同时走**降级逻辑（Fallback）**兜底，避免局部故障演变成全链路雪崩。

---

## 一、 为什么需要熔断？故障是如何蔓延的

在分布式微服务调用链中，假设存在调用路径 `A -> B -> C`（例如：`订单服务 -> 库存服务 -> 数据库`）：

1. **下游变慢或报错**：`C` 出现慢查询或局部节点宕机，响应时间从 `10ms` 拉长到 `5s`。
2. **上游资源耗尽**：`B` 的工作线程或连接池被大量阻塞等待 `C` 的请求占满，新请求排不上队，导致 `B` 自身也响应超时或抛出异常。
3. **级联雪崩**：`A` 调用 `B` 同样超时失败，`A` 的资源也被拖垮，最终整个系统不可用；甚至下游 `C` 恢复后，也会因上游积压的重试和请求洪峰再次被打垮。

> **核心价值**：熔断器的核心在于**止损隔离**——将“等超时失败”变成“立刻失败”，既保护上游自身不被拖垮，也给故障下游留出喘息和恢复的时间。

---

## 二、 熔断器的核心状态机

绝大多数主流熔断框架（如 Resilience4j、Sentinel、Hystrix）都围绕**三态状态机**运转：

| 状态 | 行为表现 | 触发转换的条件 |
| :--- | :--- | :--- |
| **闭合（Closed）** | 正常放行请求，持续统计滑动窗口内的失败率、慢调用比例和最小请求数。 | 当失败率或慢调用率达到阈值（且样本量满足最小请求数）时，切换至 **打开**。 |
| **打开（Open）** | **直接拒绝调用**，立即抛出熔断异常或执行降级方法，不再访问下游。 | 经过设定的“休眠窗口 / 熔断时长”（如 `10s ~ 30s`）后，切换至 **半开**。 |
| **半开（Half-Open）** | 放行少量“探测请求”（如 `5 ~ 10` 个）去试探下游是否已恢复。 | 若探测请求成功率达标，切回 **闭合**；若仍有失败，立刻回到 **打开** 并重新计时。 |

### 统计窗口的关键细节
* **滑动窗口统计**：通常基于**滑动时间窗口**（如最近 10 秒）或**滑动计数窗口**（如最近 100 次调用）计算错误率与慢调用比例。
* **最小请求数保护**：必须设置最小样本阈值（例如至少有 20 次调用才计算失败率），防止低流量时段因 1 次偶发网络抖动就误触发熔断。

## 三、 熔断与超时、降级、限流的分工

这四个高可用治理手段经常配合使用，但在调用链路中的职责各有侧重：

* **超时（Timeout）**：单次调用的“最长等待时间”，防止请求无限挂起；超时往往是计入熔断统计的“失败”指标之一。
* **熔断（Circuit Breaking）**：针对**下游故障率过高**的保护机制，重点是“切断坏依赖，快速失败 + 触发降级”。
* **降级（Fallback）**：熔断触发或系统承压时执行的**兜底方案**，例如返回缓存数据、空列表或友好提示，保证核心主链路可用。
* **限流（Rate Limiting）**：针对**自身或下游流量过大**的保护机制，按 QPS 或并发数拦截超出水位的请求，防止系统被突发流量打爆。

---

## 四、 常见降级兜底策略

熔断跳闸后，通常根据业务重要性采取以下几类降级方式：

1. **返回静态默认值 / 空兜底**
   * *场景*：商品详情页的“猜你喜欢”推荐接口熔断后返回空数组，不影响用户查看主商品信息与下单。
2. **返回缓存 / 历史快照数据**
   * *场景*：实时配置中心或行情服务异常时，读取本地内存缓存或 Redis 中的旧数据，牺牲强实时性换取可用性。
3. **异步补偿 / 排队削峰**
   * *场景*：积分发放、日志上报等非强实时业务，先写入本地表或发送至消息队列（MQ），待下游恢复后再异步对账补齐。
4. **关闭非核心分支，保核心主流程**
   * *场景*：大促峰值期间主动降级勋章展示、优惠券推荐等边缘能力，将服务器资源集中留给下单与支付链路。

---

## 五、 工程落地的关键注意事项

* **区分业务异常与系统异常**
  * 参数校验失败、库存不足、余额不足等正常业务报错，**不应计入**熔断失败率；只有超时、连接拒绝、HTTP 5xx 等系统级故障才应触发熔断。
* **合理配置阈值与休眠时间**
  * 阈值过低会导致系统频繁抖动（在 `打开 -> 半开 -> 打开` 之间反复横跳）；休眠窗口过长则会导致下游恢复后仍长时间无法提供正常服务。
* **降级逻辑本身必须轻量且安全**
  * `Fallback` 方法应尽量简单可靠，避免在降级逻辑中再次发起高风险的远程调用，防止“降级逻辑引发二次故障”。
* **完善监控与告警联动**
  * 熔断器的状态变更（尤其是 `Closed -> Open`）必须接入监控指标与告警通知，帮助研发人员第一时间定位下游真实故障或调优配置参数。
