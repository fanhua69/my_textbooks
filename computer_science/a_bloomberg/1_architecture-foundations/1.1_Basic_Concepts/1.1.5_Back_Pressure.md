# 1.1.5 Back_Pressure

**介绍**: Back_Pressure

Backpressure（背压），中文通常翻译为：反压、背压或流量反压。

它是高性能并发系统、消息队列、网络通信和流式处理中的一个重要概念。

一句话理解：
当下游（Consumer）处理不过来时，向上游（Producer）施加压力，让上游减慢发送速度，避免系统被数据淹没。

1. 先看一个生活中的例子
想象一条生产线：

- 上游 Producer：生产产品，每秒生产 10,000 件。
- 下游 Consumer：每秒只能处理 3,000 件。
- 中间 Queue：暂存尚未处理的产品。
那么：
项目	速度
Producer	10,000 条/秒
Consumer	3,000 条/秒
Queue 增长速度	7,000 条/秒

如果一直这样运行，Queue 最终会耗尽内存。

这就是典型的 Producer 生产速度超过 Consumer 消费速度。

Backpressure 就是解决这个问题的机制。
2. Backpressure 怎么解决？
核心思想是：让上游知道下游已经忙不过来了。

常见方法有：
方法	工作原理
Throttling	限制 Producer 的发送速率
Blocking	Queue 满了，Producer 等待
Bounded Queue	限制队列最大容量
Dropping	丢弃部分数据
Load Shedding	主动丢弃低优先级请求
Feedback	下游向上游反馈处理能力

例如：
Producer
   |
   | 10,000 msg/s
   v
+----------------+
| Bounded Queue  |
| Capacity: 1000 |
+----------------+
   |
   | 3,000 msg/s
   v
Consumer


当 Queue 满了：
Producer ----X----> Queue (FULL)


Producer 必须等待、降低发送速度，或者根据业务策略丢弃数据。

这就是 Backpressure。
3. C++ 中如何实现？
例如使用 C++17 的 std::condition_variable 实现一个有界队列。
#include <queue>
#include <mutex>
#include <condition_variable>

template<typename T>
class BoundedQueue {
public:
    explicit BoundedQueue(size_t capacity)
        : capacity_(capacity) {}

    void push(T value) {
        std::unique_lock<std::mutex> lock(mutex_);

        // Queue 满了，Producer 等待
        not_full_.wait(lock, [&] {
            return queue_.size() < capacity_;
        });

        queue_.push(std::move(value));

        not_empty_.notify_one();
    }

    T pop() {
        std::unique_lock<std::mutex> lock(mutex_);

        // Queue 空了，Consumer 等待
        not_empty_.wait(lock, [&] {
            return !queue_.empty();
        });

        T value = std::move(queue_.front());
        queue_.pop();

        not_full_.notify_one();

        return value;
    }

private:
    std::queue<T> queue_;
    size_t capacity_;

    std::mutex mutex_;
    std::condition_variable not_full_;
    std::condition_variable not_empty_;
};


这里有两个重要机制：
- not_full_：通知 Producer 队列有空间了。
- not_empty_：通知 Consumer 队列有数据了。
注意：这个示例是教学实现，实际生产代码还需要处理 shutdown、异常和等待线程退出等问题。
4. 联系 Bloomberg Entitlement
假设 Bloomberg Entitlement 有一个权限更新系统：
       Authoritative Database
                 |
                 v
             Producer
                 |
                 v
          Message Queue
                 |
          +------+------+
          |      |      |
          v      v      v
       Server A Server B Server C
          |      |      |
          v      v      v
       Consumer Consumer Consumer


假设：
- Producer 每秒产生 100,000 条权限更新。
- 三个 Server 合计每秒只能处理 60,000 条。
那么更新积压速度就是：
\[
100000-60000=40000
\]

每秒增加 40,000 条待处理消息。

如果持续运行，延迟会越来越大。

这时可以采用：
1. 增加 Consumer 数量。
2. 对消息进行批量处理（Batch Processing）。
3. 限制 Producer 发送速度。
4. 合并同一个用户或 Security 的重复更新。
5. Queue 积压过多时触发 Load Shedding 或告警。
这里特别值得注意：增加 Consumer 数量并不一定解决问题，因为还可能受到 CPU、内存带宽、锁竞争或数据库吞吐量的限制。
5. Backpressure 和 Graceful Degradation 的区别
这两个概念经常一起出现，但不是一回事。
概念	含义	目的
Backpressure	下游处理不过来，限制上游流量	防止系统过载
Graceful Degradation	系统过载或部分故障时，降低部分服务质量	保持核心功能可用

例如一个行情系统：
- Backpressure：行情 Consumer 处理不过来，限制上游发送速率。
- Graceful Degradation：行情过载时，暂时停止发送低优先级统计信息，但继续保证核心行情数据。

6. 一个非常重要的工程原则
Backpressure 不等于简单地丢弃数据。

尤其是金融系统：
- 权限撤销（Revocation）不能随意丢弃。
- 权限更新不能因为队列满了就静默丢失。
- 可以合并重复更新，但必须保证最终状态正确。
- 必须考虑消息持久化（Durability）和重放（Replay）。
对于 Bloomberg Entitlement 这种系统，我会特别关注：

Backpressure + Bounded Queue + Durable Message Queue + Idempotent Consumer

这几个机制如何协同工作。

它们共同解决一个核心问题：
当系统某个环节处理能力下降时，如何避免压力沿着整个系统传播，最终导致级联故障（Cascading Failure）？
